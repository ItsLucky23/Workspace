# Proxmox Compose runner deployment

<!-- @covers services/compose-runner/** server/container/isolatedComposeRunner.ts -->

This runbook deploys the ADR 0288/0297 boundary: Workspaces sends unrestricted Compose over HTTPS to a
control-plane; that control-plane runs it in one full-cloned Proxmox QEMU VM per workspace. Nothing in this
service mounts the Workspaces host Docker socket.

## Topology

```text
Workspaces app -- HTTPS/Bearer --> Caddy --> runner controller --> Proxmox API
                                                    |                    |
                                                    | SSH bootstrap      | QEMU + external firewall
                                                    v                    v
                                          workspace A VM          workspace B VM
                                          systemd agent            systemd agent
                                          Docker daemon            Docker daemon
```

A compromised Compose stack may own its disposable VM. Proxmox firewall rules, not guest iptables, prevent it
from initiating traffic to the app/operator/private networks or another sandbox. Sandbox VM firewalls are wholly
runner-owned: any unexpected/manual VM rule fails provisioning because an earlier ACCEPT could bypass isolation.

## 1. Required hosts and networks

- Proxmox VE 8+ with QEMU, cloud-init and a storage backend that supports full clones.
- A dedicated bridge/subnet for sandbox VMs, for example `vmbr1` / `10.77.0.0/16`. Do not reuse the Proxmox
  management subnet or the Workspaces application network. Enable the Proxmox datacenter firewall; the runner
  also enables firewalling on every VM/NIC and fails provisioning when those API writes fail.
- The runner control-plane must reach Proxmox `:8006`, sandbox SSH `:22` and agent `:8788`.
- The Workspaces app may reach only gateway ports explicitly declared by a stack. Sandboxes must not initiate
  traffic to the app. The Proxmox firewall rules generated by the runner enforce this asymmetric boundary.
- Public DNS/TLS for the controller, for example `runner.workspace.keetlerop.nl`.

## 2. Golden VM template

Create an Ubuntu/Debian cloud-init VM with:

- Node.js 20+ (22 recommended);
- Docker Engine + Compose v2;
- cloud-init and an enabled serial console;
- a `workspaces` cloud-init user;
- no application secrets or shared guest token.

Build and install the agent from this repository before converting the VM to template:

```bash
npm run compose-runner:build
sudo services/compose-runner/scripts/install-agent.sh
```

The installer places the compiled agent under `/opt/workspaces-compose-agent`, installs a hardened systemd unit,
and grants the `workspaces` user exactly one passwordless command:
`/usr/local/sbin/workspaces-compose-agent-configure`. The controller injects a workspace-specific HMAC token only
after cloning. Convert the powered-off VM to template VMID `9000` (or set `PVE_TEMPLATE_VMID`). Keep its base disk
at or below `PVE_VM_DISK_GB`; the runner only grows disks.

## 3. Proxmox identity and permissions

Create pool `workspaces-sandboxes`, API user/token `workspaces-runner@pve!runner`, and a least-privilege role with:

```text
Datastore.Audit Datastore.AllocateSpace
Sys.Audit
VM.Audit VM.Allocate VM.Clone VM.PowerMgmt VM.Monitor
VM.Config.CDROM VM.Config.CPU VM.Config.Cloudinit VM.Config.Disk
VM.Config.Memory VM.Config.Network VM.Config.Options
```

Grant it:

- read/clone access to template VM 9000;
- allocate/configure/power permissions on pool `workspaces-sandboxes`;
- allocate-space permission on the selected storage;
- use permission for the selected bridge/SDN where Proxmox requires it.

Do not grant host shell or Datastore.AllocateTemplate. The runner puts every clone in `PVE_POOL`, marks it with
`workspaces;compose-sandbox`, and records exact ownership in the VM description.

## 4. Bootstrap SSH key

Generate a dedicated key used only for cloned sandbox VMs:

```bash
ssh-keygen -t ed25519 -f services/compose-runner/secrets/proxmox-ssh-key -C workspaces-compose-runner
```

The controller derives the public key and injects it via cloud-init. The private key is mounted read-only into the
controller. The controller runs as UID/GID `10001`, so on the Linux runner host set the private key to that owner
with mode `0400` (or provide an equivalent read-only secret mount); never make it world-readable. The guest sudo
rule permits only the configure helper; it does not grant a general root shell command.

## 5. Configure and deploy the controller

```bash
cd services/compose-runner
cp .env.example .env
# fill every blank secret/address and review every CIDR
docker compose up -d --build
```

Generate independent secrets:

```bash
openssl rand -hex 32  # RUNNER_BEARER_TOKEN
openssl rand -hex 32  # RUNNER_GUEST_TOKEN_SECRET
```

Important settings:

- `PVE_CONTROLLER_SOURCE_CIDRS`: addresses allowed to call the VM agent.
- `PVE_APP_SOURCE_CIDRS`: Workspaces app addresses allowed to call labelled service gateway ports. Empty means no
  cross-daemon service ingress; an `up` that declares gateway ports then fails closed instead of returning an
  unreachable/accidentally exposed endpoint.
- `PVE_OUTBOUND_DENY_CIDRS`: private/operator/metadata destinations blocked by the hypervisor.
- `PVE_OUTBOUND_ALLOW_CIDRS`: narrowly scoped exceptions that are inserted before denies, e.g. an operator egress
  proxy or private DNS resolver.
- `RUNNER_IDLE_GC_HOURS`: empty VMs are removed after this idle period. An unreachable VM is forcibly removed after
  twice this duration because sandboxes are disposable execution state. GC and API operations share a per-workspace
  lock and GC re-reads Proxmox metadata after acquiring it, so a stale pre-lock timestamp cannot delete active work.
- `RUNNER_DESTROY_ON_LAST_DOWN=1`: optional immediate VM deletion after its final stack is removed.

The controller container is read-only, drops Linux capabilities, has no Docker socket and is limited to 1 CPU,
512 MiB and 128 PIDs. Run exactly one controller replica: per-workspace and cluster-allocation locks are in-process;
Proxmox remains the durable state source, but this first implementation does not claim HA control-plane scheduling.
Caddy terminates public TLS. The public health check is `GET /healthz`.

## 6. Connect Workspaces

Set these on the Workspaces deployment and restart it:

```env
WS_COMPOSE_RUNNER_URL_TEMPLATE=https://runner.workspace.keetlerop.nl/workspaces/{workspaceId}/
WS_COMPOSE_RUNNER_TOKEN=<same value as RUNNER_BEARER_TOKEN>
```

The existing application calls:

- `POST /workspaces/<id>/v1/compose/up`
- `POST /workspaces/<id>/v1/compose/down`

The URL workspace id and JSON body must match exactly. Requests are capped at 1 MiB, responses at 64 KiB and
operations are serialized per workspace. `WS_COMPOSE_RUNNER_TIMEOUT_MS` defaults to ten minutes so a cold full
clone is not cut off by the old one-minute local-Docker timeout; it remains bounded to at most thirty minutes. Reset is operator-only and requires an exact confirmation header:

```bash
curl -X POST \
  -H "Authorization: Bearer $RUNNER_BEARER_TOKEN" \
  -H "X-Runner-Confirm: <workspaceId>" \
  "https://runner.example/workspaces/<workspaceId>/v1/sandbox/reset"
```

## 7. Exposing services back to Workspaces

Same-daemon service DNS does not exist across the VM boundary. A Compose service explicitly opts into a gateway
using labels:

```yaml
services:
  db:
    image: postgres:17
    ports:
      - "5432:5432"
    labels:
      io.luckystack.gateway.ports: "5432"
      io.luckystack.gateway.env.DATABASE_URL: "postgres://app:secret@{gatewayHost}:5432/app"
```

The guest agent reads normalized `docker compose config --format json`, accepts at most 32 valid ports, substitutes
`{gatewayHost}`, and returns only valid bounded env keys. Docker/Compose subprocesses receive a minimal allowlisted
environment, so `${AGENT_BEARER_TOKEN}` and unrelated host secrets cannot be interpolated into user YAML. The controller then opens those ports at the Proxmox
firewall only for `PVE_APP_SOURCE_CIDRS`. User-provided values remain workspace-controlled data; do not place host
or cross-tenant credentials in these labels.

## 8. Verification

Repository-verifiable:

```bash
npm run compose-runner:build
npx tsx tests/unit/composeRunnerService.test.mts
npx tsx tests/unit/proxmoxSandboxProvider.test.mts
npx tsx tests/integration/composeSandboxAgent.test.mts
```

Required live acceptance on the actual Proxmox host:

1. Up creates exactly one full-cloned QEMU VM with configured CPU/RAM/disk limits.
2. Privileged Compose and `/` bind mounts can own only that VM.
3. A container cannot reach Proxmox management, Workspaces app, metadata (`169.254.0.0/16`) or another VM.
4. The app can reach only explicitly labelled gateway ports; undeclared ports remain closed.
5. A second workspace gets another VM/IP/token and cannot call the first agent.
6. Down removes containers/volumes; GC/reset destroys the VM and full-clone disk.
7. Controller restart reconstructs workspace ownership from Proxmox metadata without a local database.

Do not claim production isolation before all seven pass against the chosen bridge/firewall topology.
