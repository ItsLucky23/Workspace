**Never remove these guards to silence the linter.** They are correct defensive code. The proper fix is project-wide: enable `compilerOptions.noUncheckedIndexedAccess` in `tsconfig.json`. Same for `@typescript-eslint/no-empty-function` on the not-yet-wired Fase-1 stub handlers (Board menu items, Terminals actions, the `WorkspacesShell` notification/FAB `noop`) — they resolve when their feature is wired in Fase 1, not by faking a body.

### 0002 — Two framework gotchas when adding _api routes with server-side deps in this project

**0002** · high · src/workspaces/_api · tags: api, devkit, validation, server-bundle, imports · 2026-07-01

**Per-route escape hatch for the validator:** add `export const validation = 'relaxed' as const;` to the route. `resolveValidationMode` maps `'relaxed'` (or `{ input: 'skip' }`) to skip the strict `validateInputByType`; the generated zod `apiInputSchemas` (`.strict()`) + the handler's own checks remain the real input guard. (A proper fix is a devkit change to not recurse the type context — until then, every new Workspaces `_api` route needs this.) **Put any RUNTIME value a route needs under `server/`**, not `src/…/_functions/`. Import TYPES from `src/` (they erase) but the values from `server/`. E.g. the RBAC `OP_CAPABILITY`/`CAP` map lives in `server/control/rbac.ts`; `controlApi.ts` keeps the `ControlOp` types + client-facing `CONFIRM_REQUIRED`. **The HTTP body for an `_api` POST is the `data` object DIRECTLY** (not wrapped in `{ data: {...} }`) — the framework passes the parsed body to the handler as `data`. (`apiRequest` sends the correct shape; only hand-rolled curl tests get this wrong.) These do NOT affect the socket transport or the framework's own `apiRequest` client; they surfaced during raw-HTTP E2E testing + server-side route wiring.

### 0003 — tenantDb's $extends must inject workspaceId even when the query has no `where` (no-arg findMany leaked cross-tenant)

**0003** · critical · server/tenant · tags: multi-tenancy, security, prisma, tests · 2026-07-01

**For every non-create tenant operation, force `where.workspaceId` — create the `where` if none exists.** Only `create`/`createMany` inject into `data`; `upsert` needs BOTH (`where` + `create`). The fix: ```ts if (operation === 'create') { a.data = { ...data, workspaceId }; return query(args); } if (operation === 'createMany') { /* map rows + workspaceId */ return query(args); } const where = a.where; a.where = where && typeof where === 'object' ? { ...where, workspaceId } : { workspaceId }; if (operation === 'upsert') a.create = { ...a.create, workspaceId }; ``` **Always test tenant isolation with ≥2 workspaces and a NO-ARG read.** A single-tenant test can never catch a scoping leak. `tests/integration/tenant.test.mts` now asserts a bare `findMany()` inside `runInTenant(wsA)` returns only wsA's rows. General: prefer verifying an isolation *guarantee* over the happy path — the happy path passed for months here while the guarantee was broken.

→ `docs/lessons/0003-tenantdb-no-arg-findmany-leak.md`

### 0012 — prisma generate EPERMs on the locked query-engine DLL — never blanket-kill node, never --no-engine

**0012** · high · prisma, schema-change, windows, dev-server · 2026-07-08

**Find the exact holder, don't blanket-kill `node`** (that would also kill Claude Code, MCP servers, the other agent). Identify it: `Get-Process node | ? { $_.Modules | ? { $_.FileName -like '*query_engine-windows*' } }`, then `Get-CimInstance Win32_Process -Filter "ProcessId=<id>"` for the command line + parent chain. If a **supervisor** (`@luckystack/devkit` `supervisor.js`) owns it, stop the SUPERVISOR (and the launching `npm run server` / cmd), not just the server child, so it stops respawning — then regenerate, then *restart `npm run server`** to leave the environment as you found it. The `/goal` "backend DOWN on schema change" authorization covers this. The DLL on disk is version-tied (not schema-tied); for an ADDITIVE optional field only the client TS types need refreshing, but you still must regenerate in normal (library) mode with the DLL free. **Never use `prisma generate --no-engine`** in this repo — it breaks the runtime datasource. If you tried it, recover with a normal `npm run prisma:generate` once the DLL is free.

### 0014 — On MongoDB an omitted optional field is ABSENT, not null — `{ field: null }` never matches it, so freshly written rows are invisible to their own queries

**0014** · high · prisma, mongodb, schema-change · 2026-07-19

On MongoDB, **write nullable state fields explicitly as `null` on create** whenever a query filters on them. `purgedAt: null` in the `create` data is the whole fix. When a query must also survive rows written before that rule existed, match both: `{ OR: [{ field: null }, { field: { isSet: false } }] }`. Symptom to recognise fast: *the write succeeds and a raw query by id finds the row, but the filtered query does not.* Before suspecting the client, the schema push, or the tenant extension, check whether the filtered field was ever actually written.

### 0015 — The dev backend hops ports and records the real one in dev-server.json — restarting "the" configured port leaves the browser on a stale backend

**0015** · high · dev-server, browser-testing, windows · 2026-07-19

**Read `node_modules/.luckystack/dev-server.json` to find the backend the browser is actually using.** Its `pid` is the one to stop; `config.ports.ts` is the *preferred* port, not the live one. After a restart, re-read that file and confirm the port changed as expected — do not assume the configured port is the live one. Before starting a fresh backend, check for orphans: `Get-CimInstance Win32_Process -Filter "Name='node.exe'" | ? { $_.CommandLine -like '*devkit*supervisor*' }`. Stop the **supervisors**, not their children, or they respawn (see lesson 0012, which is the same trap seen from the Prisma-DLL side). Symptom to recognise fast: *the code is provably correct when called directly, but the browser shows the old behaviour across a hard reload.* Before re-checking the code again, prove the running server executes it — a one-line `console.log` and a page load answers it in seconds. E2E tests that fetch `http://localhost:<configured port>` directly can pass against a *different* instance than the browser uses. That is exactly how this stayed hidden: the e2e suite went green while the UI stayed stale.
