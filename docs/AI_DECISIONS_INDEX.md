## Summaries

### 0001 — Embed per-stage config as composite types, keep loose ObjectId refs, and omit the framework-provided identity models in the Workspaces V1 Prisma schema

**0001** · accepted · tags: workspaces, data-model, prisma, mongodb, lane-b · 2026-07-01

1. **Embed per-stage config as Prisma composite `type` blocks** (`StageCommandCfg`, `StageToolCfg`, `StageStatusCfg`, `StageProcessCfg`, `StageModelCfg`, …) directly on `PipelineStage`, mirroring the prototype's flattened `PipelineStageCfg` — not normalized child collections. 2. **No wrapper `Pipeline` model.** `PipelineStage` belongs to a `Project` via `projectId`. The one V1 ticket-pipeline per project is just its ordered stage list. 3. **Loose `@db.ObjectId` reference fields, no formal Prisma `@relation`s.** Delete-cascade (`04b §11d`) and tenant isolation are Conductor / app-enforced, matching the single-writer model + the `$extends` where-injection isolation. 4. **Leave `User` untouched and add no `OAuthAccount`.** Framework auth + `User.provider` cover V1 identity; Workspaces adds only `SshKey` (B-05 terminal gate) and `PushSubscription` (web-push) as framework-global rows. 5. **`String` + a value-listing comment for growth-tolerant product fields**, not Prisma enums (only the framework's own `LANGUAGE`/`THEME`/`PROVIDERS` enums stay).

→ `docs/decisions/0001-workspaces-v1-schema-shape.md`

### 0002 — In Fase 1 the control-API enqueues to an in-process serial Conductor; the Redis signal-log + lease land in Fase 2

**0002** · accepted · tags: workspaces, control-api, conductor, fase-1, orchestrator · 2026-07-01

*In Fase 1 the control-API handler enqueues to an IN-PROCESS serial Conductor executor** (a single-writer promise-chain/mutex inside the one running web-app/dev process), which executes each op via `tenantDb` under `runInTenant(workspaceId)`. The *Redis-backed signal-log + `lease:orchestrator` + the out-of-process drain loop land in Fase 2** when the orchestrator process actually splits out (Lane A, A3). The `ControlRequest`/`ControlAck` contract and the enqueue→Conductor→`ws-ai:*` shape are unchanged — only the *transport* of the enqueue (in-memory queue vs Redis list) and the *host* of the drain (same process vs leased orchestrator) differ between phases.

→ `docs/decisions/0002-fase1-inprocess-conductor.md`

### 0004 — App-owned AES-256-GCM encryption for per-workspace secrets

**0004** · accepted · tags: security, secrets, workspaces, gitlab · 2026-07-01

Encrypt these secrets in the app with **AES-256-GCM**, in `server/crypto/secretBox.ts` (`encryptSecret`/`decryptSecret`), keyed by a single app key from `WORKSPACES_ENC_KEY` (any string, SHA-256-hashed to 32 bytes; resolved at boot like any env, so it can be a secret-manager pointer). Stored format is self-describing: `v1:<iv>:<tag>:<ct>` (base64). The **Conductor** is the only writer (B-23) — `gitlab-settings` encrypts on write; a Fase-2 GitLab client decrypts on use.

→ `docs/decisions/0004-app-owned-secret-encryption.md`

### 0005 — The write path splits into per-action typed `_api` routes (not `_sync`) — realtime `_sync` deltas deferred to a browser-testable session

**0005** · superseded · tags: workspaces, control-api, typed-routes, fase-0, transport · 2026-07-02

*Split the write path into one typed `_api` route per action** (`quickAdd_v1`, `sprintCreate_v1`, …), each with a fully-typed `ApiParams.data` payload, so the generated type-map types the client's `apiRequest({ name: 'workspaces/<op>', … })` call end-to-end. Each route stays thin: validate → `hasCapability` RBAC (the shared B-28 gate extracted to `server/control/rbac.ts`) → **enqueue onto the existing serial Conductor** (preserving serial write-ordering + the `WorkspaceSignal` event-recorder). The `WorkspacesCtx` interface is unchanged (it already exposes typed helpers like `quickAdd`/`sprintCreate`), so only each helper's implementation in `WorkspacesProvider` moves from the generic `control()` to its typed route — **no consumer/page changes**. Migration is incremental + always-green: the legacy `workspaces/control` route keeps serving not-yet-migrated ops until every op has moved, then it (and the generic `control()` client helper) are removed.

→ `docs/decisions/0005-per-action-typed-api-write-routes.md`

### 0006 — In-workspace writes broadcast a per-action `_sync` delta the client merges (no refetch)

**0006** · accepted · tags: workspaces, realtime, sync, transport, control-api · 2026-07-02

*Every in-workspace write is a per-action `_sync` event that broadcasts its DELTA to the workspace room (room code = workspaceId); every client — including the sender — merges the delta into local state via `upsertSyncEventCallback`. No refetch.**

### 0007 — Pluggable AI-provider layer — features resolve a backend at dispatch, never hardcode one

**0007** · accepted · tags: ai, architecture, orchestrator, extensibility · 2026-07-02

Introduce a generic AI-provider layer under `server/ai/`: **`types.ts`** — the shared contract: `AiProviderId`, `AiFeature`, `AiProvider` (`available()` + `complete()`), and the request/result shapes. **`providers/*`** — one standalone handler per backend: `claude-cli` (drives the interactive PTY in a scrubbed env → Max subscription, reading the final message off the Stop hook via `--settings`, never `-p/--print`) and `gemini-api` (headless Generative Language API call, gated on `GEMINI_API_KEY`). **`assignments.ts`** — the single feature→provider map, with a `resolveAssignment` seam that a per-workspace/user override (a future picker UI backed by a DB setting) plugs into without touching feature code. **`registry.ts`** — `runAiCompletion(feature, req, overrides?)`: resolves the assigned provider, gates on `available()`, and dispatches. ### 0008 — Container runtime model — clone-into-volume, name-based idempotency, off-chain provisioning

**0008** · accepted · tags: container, runtime, orchestrator, git, security · 2026-07-02

**Worktree = `git clone --single-branch` into a container-owned volume, NOT a bind-mount of the host `git worktree` checkout** (`07b §4`, Q-CT-WORKTREE). A git worktree's `.git` is a *gitdir pointer* back to the main repo; bind-mounting only the worktree dir leaves a dangling pointer that breaks git on the first command inside the container. The clone is self-contained. The `DEV-####` branch (cut at the frozen commit in phase 1b) is the clone's `--branch`, so its tip IS the frozen commit — no detaching checkout. **`git config --system safe.directory '*'` is BAKED into L1.** The RO `/mirror` (host clone) is host-uid-owned; git's dubious-ownership guard refuses it. `-c safe.directory` is ignored by git for this key BY DESIGN — only system/global config is honored — so it must live in the image. **Name-based idempotency, no persistence yet.** A container is keyed by `ws-<safe(workspaceId)>-<safe(ticketKey)>`; re-activation reuses/ restarts the named container. V1 does NOT write an `AgentSession` row — the container name + docker labels (`org.workspaces.workspace` / `.ticket`) are the lookup, so no schema change. **Provisioning runs OFF the conductor serial chain** (fire-and-forget at aiEnabled activation). `docker` clone+run is ~10s; the authoritative stage move must return fast for the realtime board. Best-effort: a launch failure is logged, never fails the move. **`docker exec` for terminals in V1**, gated on the workspace label (never exec into a foreign container). The full in-container pty-agent (durable scrollback, crash-resume, `07b §9`) is deferred.

→ `docs/decisions/0008-container-runtime-model.md`

### 0009 — Register-flow AI operations — direct _api, draft-then-review, pure-context prompting

**0009** · accepted · tags: ai, register-flow, dockerfile, docs, security · 2026-07-02

**AI operations are direct `_api` routes, NOT Conductor control-ops.** `generateDockerfile` / `generateProjectDoc` / `aiChat` each run a multi-second-to-minute AI turn. The Conductor is the single SERIAL writer for authoritative state; routing a 2-minute turn through it would stall every other write. So AI ops call the provider layer directly from an `_api` handler (capability-gated), and only their *result* — if it mutates state — goes through a normal control-op (e.g. the Workspace-AI chat's accepted proposal dispatches `bulk-move`). **Generated artifacts are a reviewable DRAFT, never auto-applied.** The Dockerfile is written to `data/workspaces/<id>/draft.Dockerfile` and validated to extend the L1 base (`FROM workspaces/base` only, Q-CT-DOCKERFILE-TRUST) — but NOT built or committed. The user reviews (Monaco slice) before it becomes the repo's `.workspaces/Dockerfile` and an L2 image. Docs land as `generated` InfoSources the user can see + toggle, not silent truth. **Pure-context prompting.** The `claude-cli` provider runs in a scratch cwd (not a repo checkout), so AI-gen prompts pass the repo content inline (manifests + file tree) and explicitly forbid filesystem/tool access ("use ONLY the provided files"). See lesson 0008.

→ `docs/decisions/0009-register-flow-ai-operations.md`

### 0010 — Per-container VS Code editor with a projected per-user profile (extensions + auth)

**0010** · accepted · tags: editor, container, extensions, auth, multi-tenancy · 2026-07-03

1. **The full editor runs per-ticket, INSIDE the ticket container** (openvscode-server on the fixed in-container port, exposed via the Caddy route — [0008], CODE_EDITOR §1). Not a central editor. 2. **A durable per-user editor PROFILE is projected into each editor session**, so extensions + auth follow the user. The profile is the openvscode `--user-data-dir` (settings, `globalStorage`, and the **secret storage** where extension auth tokens live) + the `--extensions-dir`. 3. **Projection is copy-in / capture-back via `docker cp`** at editor-session start/stop (NOT a live shared volume), because: the editor server starts via `docker exec` on an already-running container, so a volume mount (which is fixed at `docker run`) would force a change to the container-launch path; copy-in via `docker cp` keeps the whole mechanism in the editor layer with zero container-launch change; it avoids two concurrent editors (same user, two tickets) corrupting one shared user-data-dir — each session gets its own in-container copy, and changes are captured back to the per-user store on install/login events + session end. Store location: `data/editor-profiles/<userId>/{user-data,extensions}` (host, gitignored, tenant- scoped). Reuses the `runInTenant` boundary like every other orchestrator path.

→ `docs/decisions/0010-per-container-editor-with-user-profile.md`

### 0011 — Git/workflow customization is split into structured per-workspace config vs skill/context-doc guidance, and the preview reverse-proxy is a pluggable Caddy/nginx provider

**0011** · accepted · tags: git, hosting, proxy, workflow, config · 2026-07-03

*A. The line = "does CODE act on it, or does the AI just READ it?"** **Code acts → structured config.** A per-workspace `GitConfig` (`Workspace.gitConfig` JSON): `branchStrategy` (ticket-prefix | typed | custom template), `pushPolicy`, `targetBranch`, `protectedBranches`, `commitSigning`. `server/git/branchStrategy.ts` is the pure resolver: `resolveBranchName` (called once at branch creation, persisted on `Ticket.branch`) + `deriveHostSlug` (the same branch → a valid RFC-1123 preview subdomain). One source of truth, two consumers (git worktree/container naming + the proxy host). **AI reads → skill/context-doc guidance.** "How to commit / conventions" lives in the EXISTING InfoSource layer (context-docs + `sourceIds`/`enabled`), NOT in config. A curated *starter library** (`server/bootstrap/starterLibrary.ts`) seeds disabled `source='starter'` context-docs a user toggles on — "a nudge, not a blank page". The load-bearing wire that was deferred — injecting a stage's context-docs into `CLAUDE.md` — is now built (`stageRunner` loads enabled starter + per-stage `sourceIds` docs → `renderStage` inlines them).

→ `docs/decisions/0011-pluggable-proxy-and-git-workflow-config.md`

### 0012 — The AI engine and a human's live editor never run on a ticket's container at once (edit-lock), and stale proxy routes self-heal on boot

**0012** · accepted · tags: editor, engine, concurrency, proxy, safety · 2026-07-03

*A. Mutual edit-lock (`server/orchestrator/editGuard.ts`).** **Engine side (enforced, `conductor.provisionContainers`):** before auto-running a stage turn, `isEditorRunning(workspaceId, ticketKey)` checks for a live openvscode-server process in the container; if present, the turn is **skipped + logged** (re-entering the stage re-triggers it). The engine never clobbers a human's open session. **Editor side (`ticketEditGuard`, a helper the open-flow calls):** refuse to open the editor when the current stage is not `userEditable`, or the AI is mid-turn (a busy `worker` AgentSession on the ticket). Provided here; wired into the open-flow by the editor owner.

→ `docs/decisions/0012-editor-engine-edit-lock-and-proxy-boot-reconcile.md`

### 0013 — Engine control-plane completion — push-on-approval, pause/kill controls, off-chain realtime broadcast, and preview exposure

### 0021 — Real git-merge for the built-in MR review (approval-gated, conflict-safe, revertible)

**0021** · accepted · tags: workspaces, mr-review, git, merge, approvals · 2026-07-03

**`repoStore.mergeBranches(workspaceId, target, source, strategy)`** does a real merge in the per-workspace **bare clone** via a THROWAWAY merge-worktree (never a long-lived checkout): add a worktree on `target`, `git merge` (`--no-ff` / `--squash` / `--ff-only` per the MR's strategy), and on success the target ref advances. On conflict the merge is **aborted** (target untouched) and the conflicting files are returned. `revertMergeCommit` rolls a merge back with a history-preserving **git-revert** (auto `-m 1` for a real merge commit, plain revert for a squash), never a destructive reset. **Serial by the existing lease.** Merges run inside the Conductor's op switch, which already holds the per-workspace write-lease (ADR 0015), so two merges can't race the same target. No new lock. **`mergeMr` enforces the approval gate:** it requires ≥1 approval whose `headSha` equals the MR's current head (a *stale* approval — cast before the branch advanced — does not count). Only then does it call `mergeBranches`, record the merge commit sha (`MergeRequest.mergedSha`, new field) for rollback, and flip status. On conflict it flips status to `conflict` and returns the files. **`mr-rollback` control-op** (+ RBAC `workTickets`, + the `mrAction` route's action map) reverts a merged MR and reopens it for re-review — mirroring the existing mr-* ops, no new *verb* on the frozen AI channel. **UI:** the Merge button is disabled until a fresh approval exists (with a tooltip); a conflict shows a `conflict` status + a "Retry merge"; a merged MR shows a **Revert** button; the transient merge/rollback outcome (no-approval / conflict + files) is toasted via a non-persisted `actionResult` carried on the returned view. i18n en/nl/de/fr.
