# Workspaces — Gap Scan (2026-07-17)

Workspaces is far past prototype: the dev-pipeline Conductor, the Designer, the ffmpeg render pipeline, YouTube/TikTok publishing, Documents, the universal Skills layer, and the RAG/provider backbone are all real, working, end-to-end systems — repeatedly verified by reading the actual code, not the docs. For a single dev workspace the core promise already holds today: the AI does the work and the human approves. The single biggest theme of what's missing is **orphaned backends** — capabilities fully built inside one module whose data/flow edge into the next module was never drawn: an autopilot chain no form can address, Studio landing pages with no button to ship them live, a demo-capture no deploy event can trigger, Documents that can't see the board. The second recurring theme is **phone-first loop integrity** — the approve/answer write is fire-and-forget with no offline feedback, notifications dead-end without deep-links, and several surfaces named as phone-first (Designer, Studio, even creating a second workspace) never got a mobile pass. A handful of genuinely-new capabilities the vision names — newsletter send, podcast/audio distribution, dubbing/localization — have no home in the code at all. Net: the hard engines exist and most remaining work is finishing-touch or wiring effort, not rebuilds — and the fastest wins simply reconnect backends that are already built on both ends.

## New tools & modules

Whole capabilities worth building, clustered across dimensions and ordered by impact. Effort: S (days) / M (1–2 weeks) / L (multi-week).

### 1. Newsletter / email-marketing delivery — **HIGH · M**
Studio's Marketer already generates newsletter/campaign copy (`email` artifact kind), but there is no subscriber-list model, no send integration, and no open/click tracking. `@luckystack/email` is used only for account email-change, never outbound marketing. Build the missing delivery layer: list management, send, and campaign metrics.
- **Why:** The vision names an owned-audience channel; today the AI writes email nobody can send. ~80% of the work (copy generation) already exists — only list/send/tracking is missing, making this the highest-leverage new module.
- **Evidence:** `src/workspaces/studio/page.tsx:24,249` (EmailPreview, copy-only); `functions/settings/_api/requestEmailChange_v1.ts` is the only non-auth `@luckystack/email` use.

### 2. Autopilot publishing reliability & health layer — **HIGH · M**
Cluster of five gaps that all break the "10 channels on autopilot" promise: (a) failed publishes are silent — no notification/push, unlike every other automation action; (b) once a job flips to `error` it vanishes from the queue view; (c) no retry (auto or one-click) for transient failures; (d) no dead-OAuth detection or reconnect CTA; (e) no burst/quota staggering when many posts fire in one cron tick. Build a reliability layer: notify-on-failure, retry with 429-aware backoff, per-connection health state + reconnect prompt, staggering, and a per-channel publish-health dashboard ("all 10 channels still posting on schedule").
- **Why:** Unattended multi-account publishing is the flagship content use-case; today a stopped channel is invisible until the user opens every piece. Directly serves the phone-first approve-from-notification loop.
- **Evidence:** `server/content/publish.ts` runScheduledPublish (no notification on error, sequential loop, no retry); `server/content/publishOAuth.ts` getValidConnection (`if (err || !refreshed) return stored`); `src/workspaces/scheduled-posts/page.tsx` (`status !== 'scheduled'` filter hides errors); prisma `PublishJob` (no attempts/retry field); `content/insights/page.tsx` (no publish-status aggregation).

### 3. Raster thumbnail studio — generate, attach, upload, A/B — **HIGH · M**
Three findings collapse into one: Studio's `thumbnail` kind is HTML-only (renders in an iframe, can't feed a video), the render pipeline has zero thumbnail-composition code, and `publish.ts` never calls `thumbnails.set`/TikTok cover — so every posted video uses the platform's auto-frame. Build a real image-composite step (background/frame + bold headline + optional face/logo, multiple aspect variants) producing a downloadable/uploadable PNG, wire it into publish, and add thumbnail-variant A/B testing against view-through-rate (the shortlink A/B winner-badge pattern already proves the product can do variant testing).
- **Why:** Thumbnails were explicitly named by the owner and are the single highest-leverage YouTube CTR lever; the feature "exists" visually but produces nothing usable.
- **Evidence:** `server/studio/roles.ts:21-38,115-120,143` (thumbnail = HTML ad creative); `server/content/publish.ts` (no thumbnail upload); `server/content/render.ts` extractPoster (gallery-only frame grab).

### 4. Captions + multi-language dubbing / localization — **HIGH · L**
The pipeline runs elevenlabs voice but has no auto-caption/subtitle track, no caption styling (burned captions use bare `subtitles=` with no `force_style`, no word-by-word karaoke reveal — the dominant short-form style), and no second-language voice pass. Build: styled/animated caption generation, subtitle export, and a dub/localize workflow that re-runs the same scene decomposition through elevenlabs in additional languages.
- **Why:** Captions materially lift reach/accessibility on every short-form platform, and dubbing is a large reach multiplier that's cheap relative to value on top of the existing voice stack. Caption styling also ties into the already-built brand-kit (fonts/colors).
- **Evidence:** `server/content/render.ts` buildCaptionPassArgs:373-378 (no force_style); `src/workspaces/content/[pieceId]/page.tsx:404` (captionMode only); `server/content/voice.ts` (no second-language pass).

### 5. AI job queue — concurrency limiter + circuit breaker — **HIGH · M**
`runAiCompletion` (the single choke-point for chat, interviewer, mr-review, root-cause, plan-critique, docs-gen, scraper, custom tasks) has no in-flight cap: N cron/user triggers spawn N node-pty + `claude` processes simultaneously. There's also no circuit breaker for persistent auth failure — every turn eats the full ~90s timeout ×2 before failing. Build a semaphore/queue with a max-parallel cap plus fast-fail when the provider is known-broken.
- **Why:** The product's own vision wants scheduled/cron automation that can fire close together; uncapped PTY+REPL spawns are the classic thundering-herd that takes down a self-hosted single-VM. Broken auth silently stalls the phone-first Assistant a human is waiting on.
- **Evidence:** `server/ai/registry.ts:59-110` (retry loop, no semaphore); `server/ai/providers/claudeCli.ts:27-34,48-96` (binary-presence cache only, fresh pty per call); `server/automation/executor.ts` (direct dispatch, no queue); grep of server/ai + server/automation for `semaphore|maxParallel|pLimit|inflight` → none.

### 6. Turn observability — persisted per-tool-call audit trail — **HIGH · M**
The design corpus specifies a PostToolUse hook → `/hooks/ticket-event` endpoint appending a granular TicketEvent per tool call; it was never built. Only Stop + PreCompact hooks are wired, TicketEvents are written at coarse Conductor-action granularity, and live PTY text (`broadcastAgentTerm`) is a bare socket emit — never persisted, gone forever if nobody's watching. Build the durable per-turn record: what files were touched, what commands ran, in what order.
- **Why:** The core pitch is "the human approves." Approving without being able to later inspect what a turn actually did undermines exactly the oversight the phone-first flow depends on — and it's a gap vs. the corpus's own stated hook wiring.
- **Evidence:** `server/orchestrator/renderStage.ts:131-136` (only Stop/PreCompact); no `hooks/ticket-event` custom route in server/; `server/read/broadcast.ts:73-85` (unpersisted emit).

### 7. One-click publish for Studio/Designer artifacts — **HIGH · M**
Deploy/DNS/subdomain machinery is fully built but scoped to dev projects/services only. Studio generates landing-page/brand artifacts that can only be promoted-to-settings or sent-to-content — there's no `studio-landing-deploy` op to ship a generated landing page live on a subdomain.
- **Why:** Reusing the battle-tested deploy infra for a "ship this live" button turns Studio outputs from design artifacts someone hand-copies into a real project into actually-usable pages — a small bridge over existing infra.
- **Evidence:** `server/deploy/environment.ts` (project/service-scoped); `server/studio/generate.ts` + `src/workspaces/studio/page.tsx:47-50,152,211-224` (promote/send-to-content only, no deploy action).

### 8. Workspace cloning ("copy from existing workspace") — **HIGH · M**
D9 is documented in two build-docs as a create-flow option but has zero implementation — every workspace starts from the same blank seed. Build deep-duplicate of skills/sources/tools/env/channels/cron-triggers from an existing workspace the user owns. This also subsumes the cross-workspace skill-sharing gap (custom skills are currently trapped in the workspace they were authored in).
- **Why:** The product explicitly encourages "one workspace per channel/purpose"; without cloning, multi-workspace users pay full onboarding cost (rebuild triggers, skills, brand kit, channels) every single time.
- **Evidence:** verified-absent grep `copy-from-workspace|copyFromWorkspace|duplicateWorkspace|cloneWorkspace` over src/workspaces + server; documented in `_docs/features/01_WORKSPACE_SETUP.md`, `02_PIPELINE_PRESETS.md`; Skill model is workspaceId-only with no import/duplicate op.

### 9. Designer inspiration: full-look extraction + web discovery — **HIGH · M**
Cluster of designer gaps that together make the module's core promise real: (a) extraction captures only 30 color tokens, discarding radius/shadow/border/font/motion — the fields that actually define a Brutalist/Glassmorphism look; (b) no discovery step (no web search to *find* candidate sites — the user must already have a URL); (c) desktop-only 1440px capture, no mobile viewport; (d) "our page" URL is hand-typed instead of auto-filled from the workspace's own deployed environment. Extend extraction to the full DesignStyle/AnimSpec schema the generator already understands, add web-search discovery, add a viewport toggle, and auto-fill own-URL from the Deploy module.
- **Why:** "Compare your UI against styles found online and apply them back" only works if a style means theme+font+motion together; color-only import never actually looks like the reference once applied. This is the single highest-leverage fix for the Designer's stated purpose.
- **Evidence:** `server/designer/inspiration.ts:36,45-59,70-74` (color-only EXTRACT_SYSTEM, hardcoded 1440 viewport, full-page compare); `server/designer/generateAsset.ts` (DesignStyle/AnimSpec schema already exists); no `webSearch` in server/designer.

### 10. Workspace-wide media / asset library — **MEDIUM · M**
Every generated asset (image, voice clip, music, .glb, character) is siloed inside a single content piece — no cross-piece gallery to reuse a brand mascot, logo, or voice across pieces/channels. Build a searchable, workspace-scoped library. This also unblocks Documents reusing existing Designer/Studio/Content assets instead of regenerating lookalikes.
- **Why:** For "10 channels" and repeated brand assets, regenerating (and paying for) the same asset per piece wastes the €-metered media budget and breaks brand consistency.
- **Evidence:** `server/content/mediaAsset.ts` (per-piece scoping only, no workspace-scoped query); `server/documents/docs.ts:93-105` (generateDocumentImage always regenerates, no asset lookup).

### 11. Publish-platform expansion (Instagram / LinkedIn / X / blog-RSS) — **MEDIUM · L**
The type layer models 4 platforms but only YouTube + TikTok have upload builders; IG/LinkedIn are deliberately hidden, X and blog aren't even typed. Build the missing upload transports — Instagram Reels reuses the TikTok short-form shape almost entirely and is the cheapest next unlock.
- **Why:** "Push to 10 accounts across platforms" needs more than 2 real channels.
- **Evidence:** `server/content/publish.ts:31-38` (`BUILT_PLATFORMS=['youtube','tiktok']`, FUTURE=['instagram','linkedin']); `content/settings/page.tsx:336-339`.

### 12. Content SEO layer — **MEDIUM · S**
No keyword research, meta/title/description scoring, or tag optimization anywhere, and no blog/article SEO tooling. Build a title/description/tag optimizer with an SEO feedback loop off already-ingested publish metrics.
- **Why:** Analytics are already fetched (`publishMetrics.ts`) but dead-end at a display stat; correlating titles/tags with views is a natural high-leverage extension on existing infra.
- **Evidence:** verified-absent SEO scorer/keyword-research across server/; `server/content/publishMetrics.ts` (data ingested, unused for optimization).

### 13. Analytics-over-time / performance-trend module — **MEDIUM · S**
`publishMetrics.ts` overwrites `PublishJob.metrics` on each pull with no time-series; Insights shows only current totals. Add a snapshot/history table and per-channel/per-piece trend charts.
- **Why:** Counters are already pulled from real platform APIs; a trend chart is a small addition and is exactly the signal the ideator role needs to actually learn what performs over time.
- **Evidence:** `server/content/publishMetrics.ts` (no snapshot-date field); `content/insights/page.tsx:69-142` (current-value only).

### 14. Community-management action layer — **MEDIUM · M**
Comment inbox is read-only (fetch-and-store, no sentiment/aggregation). Build the action half: reply / AI-suggested-reply posting, plus sentiment/theme aggregation that feeds the ideator's already-wired per-channel `recentWinnersLine()` hook so real audience reactions steer the next video idea.
- **Why:** Half the value of community management (acting on and learning from what people say) is missing even though the ideator's channel-aware attachment point already exists.
- **Evidence:** `server/content/commentInbox.ts` (no reply/sentiment fn); `server/content/ideatorRole.ts:27-30` (channel-aware winners context, no comment join).

### 15. Pipeline preset / template system — **MEDIUM · M**
`Workspace.presetKey` (`simple|advanced|professional`) is documented as a create-time tier choice but is dead data — hardcoded to `'professional'` at both seed sites, with no tier fixture registry, no picker UI, and no pipeline-template save/duplicate. Build the tier registry + creation-time picker + template save/clone.
- **Why:** Every workspace — including a deliberately minimal automation-only one — gets the heaviest 7-stage opus-review pipeline; configurability is currently manual stage-by-stage deletion, which is brutal from a phone.
- **Evidence:** `server/bootstrap/seedWorkspace.ts:50,111` (hardcoded); `_docs/features/02_PIPELINE_PRESETS.md:45-73`; verified-absent `presetKey|'simple'|'advanced'` across src/workspaces/*.tsx.

### 16. Prompt-quality eval / PromptVersion A-B system — **MEDIUM · L**
`AI_QUALITY_AND_EVALS.md` designs a full loop (live golden-tickets lane, LLM-as-judge tier, `PromptVersion` model with content-hash + A/B promotion, reject/edit-as-feedback into few-shot examples). Only the free deterministic replay scorer exists — it catches structural regressions, never a semantically-worse prompt. Build the PromptVersion model, live golden lane, LLM-judge, and feedback loop.
- **Why:** The product bets differentiation on AI quality across 5+ reasoning roles, all hand-edited prompts with zero measured feedback; every tweak is currently verified only by vibes.
- **Evidence:** `_docs/AI_QUALITY_AND_EVALS.md` §3.4/4/5; verified-absent `PromptVersion|contentHash|evalScore` in schema.

### 17. Deploy history & rollback — **MEDIUM · M**
Each deploy overwrites the single `imageRef`/`deployedCommit` in place — no DeployHistory table, no "rollback to previous" op. The promote ladder is a one-way door: once a bad build reaches prod there's no built-in revert. Build a deploy-history log + rollback op. (Note: the separate redeploy-serves-stale-code bug must be fixed first, or rollback can't be trusted.)
- **Why:** A promote ladder without rollback is a real production-incident gap for a self-hosted product whose pitch is "push a fix, it goes live."
- **Evidence:** `server/deploy/environment.ts` (single imageRef overwrite); `server/deploy/promote.ts` (no history); verified-absent `rollback` in server/deploy.

### 18. Durable audit sink — **MEDIUM · M**
`AuditLog` is a plain per-workspace collection; `delete-workspace` records the intent then cascade-deletes that very row plus all prior governance events. ADR 0167 self-flags this as an open follow-up. Build a cross-tenant durable sink for governance/deletion events.
- **Why:** The exact scenario audit logs exist to catch (a compromised admin transfers ownership then deletes the workspace to cover tracks) is the one where the current implementation loses all evidence.
- **Evidence:** prisma `AuditLog` (workspaceId-only, no external sink); `conductor.ts:826-829`; ADR 0167 Consequences ("durable cross-tenant sink… is a noted follow-up").

### 19. Podcast / audio-only distribution — **MEDIUM · M**
The pipeline already generates voice + music per piece, but there's no RSS feed generator, no audio-only export/publish target, and no podcast-host integration. Build an RSS/audio publish path (and a podcast-only workspace shape).
- **Why:** A natural extension of an already-built voice/music stack; creators currently get zero credit for audio assets beyond video soundtracks.
- **Evidence:** verified-absent podcast/audiogram/rss-feed across src/workspaces; no server/content audio-publish file.

### 20. Documents authoring capabilities — templates, diagrams/wireframes, version-restore — **MEDIUM · M**
The Documents module ships with no document `kind`/templates (every doc starts blank), no diagram-as-code (mermaid) or wireframe support (the vision explicitly names "wireframes"), and a write-only revision history with no view/restore path (the DocumentRevision table is written but never read anywhere in the UI). Build a template picker, diagram rendering, and revision restore. (Related coupling gaps — linking docs to tickets/decisions, grounding drafts on board data — are separate integration work.)
- **Why:** "Document everything" degrades to a flat blank-box library; templates and diagrams cover two of the four named content types outright, and restore makes the existing DB safety net actually usable.
- **Evidence:** prisma `Document` (no `kind`); `documents/page.tsx:27-37` (title-only create); `_components/MarkdownView.tsx` (no diagram branch); `conductor.ts:2172-2176` (revisions written, no read path).

### 21. Competitor / external-site monitoring over time — **LOW · S**
`server/scraper/role.ts` fetches one page per run with no snapshot history, diffing, or change-alerting. Add a snapshot data-model + diff so a competitor's site/pricing/content can be watched over time.
- **Why:** Natural extension of "compare your UI with styles found online" into "tell me what changed"; the guarded/capped fetch plumbing already exists — this is mostly a data-model + diff.
- **Evidence:** `server/scraper/role.ts:1-40` (single fetch per run, no persistence).

## Per-module polish

Finishing touches on modules that already work end-to-end. Scope: `module-polish` + `ux-mobile` gaps only — correctness bugs, cross-module coupling, and net-new modules are covered in their own sections. Each item is tagged `(impact · effort)`.

### Dev pipeline
Solid single-writer engine (Conductor, PTY stage-runner, CI gates, MR-on-approve) plus a rich stage editor; the polish gaps sit in the seam between what the editor configures and what runtime records/honors, plus missing regression coverage.
- No persisted per-tool-call audit trail — a completed autonomous turn leaves only a self-reported `changedFiles` list; mid-turn output is an ephemeral live broadcast that's gone if nobody's watching, undercutting the approve-then-inspect promise. `(high · M)`
- Every workspace is seeded with the identical hardcoded 7-stage pipeline — the `presetKey` enum (`simple`/`advanced`/`professional`) exists but there's no template/preset picker at creation, so "configurable pipelines" means deleting stages one by one. `(medium · S)`
- WIP limit is enforced on the board but has no field in the stage editor — only settable via a raw control-API call. `(low · S)`
- The renderer's own mandated golden-fixture regression test — pinning the B-23 permission guarantees on one of the highest-blast-radius files — was never built. `(high · M)`
- The pipeline editor never shows or lets you switch which project's pipeline you're editing in a multi-project workspace. `(medium · S)`

### Designer
One of the more mature modules — full visual editor + AI generation + gallery + working inspiration/compare (INS); the recently-landed inspiration half is where the finishing gaps cluster.
- Inspiration import extracts color tokens only, discarding style/font/motion, so an imported "look" never actually resembles the reference site once applied. `(high · M)`
- Capture and compare are desktop-viewport-only (hardcoded 1440×2200) — no mobile rendering, despite the product's own phone-first output goal. `(medium · S)`
- Inspiration capture+extract is a single blocking ~3-minute request with no background/notify-when-done pattern; a backgrounded phone tab loses the result silently. `(medium · M)`
- Two overlapping "style catalog" concepts (Gallery premades vs the seeded theme-only gallery) share names (Brutalist, Minimal…) but hold different data, with no cross-link. `(low · S)`
- Compare is whole-page only — no component-level (button-vs-button) comparison, so verdicts stay generic. `(low · M)`

### Interviewer / ideas
Past the notification-only stub: repo-aware chat, structured persisted `InterviewFinding` rows, finding→ticket via the Conductor, and cron-schedulable unattended runs all work; the gaps are trust/noise and phone reachability.
- No dedup of findings across repeated/scheduled runs — duplicates and previously-dismissed ideas pile up, training the user to ignore the panel. `(medium · M)`
- The `detail` field is wired in the schema but never written or read — every finding is a bare title + one-line summary with no reasoning or file citation to judge from. `(low · S)`
- The "Generate ideas now" focus input is `hidden sm:block` — on a phone the manual run always silently runs unfocused (whole-project scope). `(medium · S)`

### Video / marketing
A genuinely deep ffmpeg pipeline (multi-clip stitch, audio mix, timed captions, CTA/watermark, aspect presets, timeline editor); gaps are visible-in-the-output finishing touches.
- Still images render as a static frame for their duration — the Ken-Burns/zoompan motion called for in the build plan was never built; this is the literal "slideshow" problem. `(high · M)`
- "fade" and "xfade" are two selectable transitions that render as the exact same crossfade — one dead option, and no transition variety despite ffmpeg supporting dozens. `(medium · S)`
- Burned-in captions have zero style/font/color control and no word-by-word/karaoke reveal (the dominant short-form style). `(medium · M)`
- The timeline editor has no drag interaction — reorder/trim are buttons and number inputs, notably clunky on a touchscreen. `(medium · M)`
- No branded intro/outro clip concept for a channel posting repeatedly. `(medium · M)`
- No one-click multi-aspect batch export — the same timeline must be re-rendered per aspect (16:9 / 9:16 / 1:1) manually. `(low · S)`

### Content automation / publishing
Real YouTube/TikTok upload adapters, encrypted multi-account OAuth, cron-fired scheduling, and an autopilot chain exist; failure-handling and multi-account safety are the weak links.
- No retry (manual or automatic) for a failed publish — `PublishJob` has no attempts field, so every transient blip becomes a permanently lost post. `(medium · S)`
- The publish composer's account picker defaults to `accounts[0]` and ignores the channel's configured default account — a wrong-account cross-post risk on every manual publish. `(medium · S)`
- No dead-connection detection or reconnect prompt for a broken/revoked OAuth account — failures are generic and undiagnosable. `(medium · M)`
- No per-channel publish-health view for the "many accounts on autopilot" case — no at-a-glance "are all 10 channels still posting?". `(medium · M)`
- No burst/quota-aware staggering when many scheduled/autopilot posts fire in the same cron tick — uncoordinated concurrent uploads hit platform quotas. `(low · M)`

### Workspace modules
Module-typing (dev/content/design/documents) is solid plumbing consumed consistently across create flows, nav-gating, and page conditionals; the gaps are everything around making a purpose-specific workspace smooth — especially from a phone.
- Creating a second/third workspace is impossible from a phone — the switcher+create UI lives in a `hidden md:flex` desktop-only header; the mobile drawer can switch but not create. `(high · S)`
- Non-dev workspaces are still seeded with the full 7-stage dev pipeline + git-workflow starter library they can never reach — dead DB rows plus irrelevant "Workflow" settings clutter. `(medium · S)`
- The documented 3-tier preset system (`simple`/`advanced`/`professional`) never reaches the UI — every workspace is hardcoded to `professional`, `presetKey` is dead provenance. `(medium · M)`
- Only Development gets a guided first-run example (sprint + starter tickets); Content/Design/Documents land on a bare empty state. `(low · S)`

### Documents
A real single-writer AI document library (four draft modes, RAG-grounded, native md/html/xlsx/docx/pdf export) with a solid core; everything around it is thin.
- No document `kind`/type or starting templates despite the spec calling for it — every doc starts blank, no filter-by-type. `(medium · M)`
- No wireframe/diagram support (mermaid/canvas) in the editor or export, though "wireframes" is a named vision content type. `(medium · M)`
- Version history is write-only — `DocumentRevision` is snapshotted on every change but never listed or restorable anywhere in the UI. `(medium · S)`
- Documents can only be hard-deleted — the `archived` field and its snapshot filter exist, but no archive/restore op (a pattern already shipped one module over in Content). `(low · S)`
- No search/filter across the document list, and the ⌘K palette doesn't index documents — even though per-document RAG chunks already exist server-side. `(medium · S)`
- No upload-and-edit round trip — an uploaded Word/PDF is an opaque attachment, never parsed into content for the AI to revise. `(medium · M)`
- AI full-document rewrites show the whole new draft with no diff against the current version — near-unworkable to review on a phone, weakening the apply-is-consent model in practice. `(medium · M)`

### Skills
The universal Skill model works at its core (5 builtins, CRUD ops, single injection helper wired into both AI choke points, real integration test); the surrounding product experience is young.
- Zero builtin skills apply to the dev pipeline — the flagship surface's injection point is correctly wired but permanently empty out of the box, so a new dev workspace sees 5 toggles that do nothing for its actual work. `(high · S)`
- No per-stage/per-surface scoping — only a workspace-wide enable plus one coarse apply-point group, so all dev stages get identical skills (the old InfoSource picker already proves per-stage granularity is expected). `(low · M)`
- The planned shared picker-UI shell (SK2) was never built — Skills got a bespoke settings list, inconsistent with the theme/style pickers it was meant to share a shell with. `(low · M)`

### Mobile / PWA UX
Phone-first plumbing is genuinely solid (manifest, dependency-free SW with deep-link push, mobile chrome, `NeedsInputBanner`); gaps concentrate at the edges of that core.
- Approve/answer writes are fire-and-forget bare `void syncRequest` with no offline/reconnect banner — a tap during a connectivity dropout silently vanishes while the UI implies success, directly endangering the core approve-from-phone loop. `(high · M)`
- iOS Safari has no PWA-install or push fallback (`beforeinstallprompt`-only; `togglePush` snaps back to off with no error) — the most common phone platform fails silently. `(high · S)`
- Sub-16px input fonts (`text-sm`/`text-xs` across 61 sites) trigger iOS Safari's auto-zoom-on-focus on every field tap. `(medium · S)`
- Interactive controls are frequently under the 44px touch-target guideline (h-9 buttons, 32px segments, 28px maximize toggle, dense terminal tabs). `(medium · S)`
- The Terminals module has no on-screen key toolbar (Ctrl/Esc/Tab/arrows), making interactive terminal use effectively impossible from a phone keyboard. `(medium · M)`
- Knowledge-graph nodes shrink to ~2–4px un-tappable radius at phone scale, dead-ending the tap-a-node interaction model. `(medium · S)`
- Designer, Studio, and MR-review ship a single desktop-oriented layout with no `isMobile`/responsive pass — despite Designer/Studio being named as phone-first surfaces. `(medium · M)`

### Assistant / RAG / AI backbone
The most mature dimension — generic provider registry with per-feature overrides, single retry choke-point, universal skills injection, unified RAG across four corpora; the gaps are load-bearing reliability and measurement thinness.
- claude-cli turn-driving uses blind fixed-timing keystroke injection (6s boot, 2.5s trust, etc.) rather than readiness detection — fragile under host load, and every reasoning feature rides this one path. `(medium · M)`
- The prompt-quality measurement loop (live golden evals, `PromptVersion` A/B, LLM-judge, reject-as-feedback) is fully spec'd but 0% built beyond the free structural replay scorer — every prompt tweak is verified only by vibes. `(medium · L)`
- The AI root-cause role reasons over merge titles alone — no diff or RAG grounding — unlike its mr-review sibling, which is weak grounding for a revert suggestion. `(medium · S)`

### Security / ops
Mostly invert-enforced controls (RBAC matrix, at-rest secret encryption, spend ceiling, HMAC webhook); most of this dimension's issues are correctness/hardening (covered elsewhere) — the polish-category gap is accessibility on the approval choke point.
- Destructive/irreversible confirm flows (`menuHandler.confirm` — env-teardown, delete-workspace, remove-member, transfer-ownership) have near-zero accessibility support (only 9 of 55 files use `aria-label`), yet they sit directly on the human-approval choke point the whole single-writer model rests on. `(medium · M)`

### Cross-cutting read

- **Deploy is the most under-wired hub.** It already provisions subdomains, URLs, and environments, but neither Studio/Designer (publish live), Content (capture-on-deploy), nor Designer-compare (autofill live URL) can reach it. ## Completeness note

A few honesty caveats about coverage, and what still has nowhere to live.

- **Correctness & security bugs are deliberately out of scope of the three sections above** — yet the security/ops dimension surfaced a serious cluster the owner should track separately: redeploy silently serving stale code (the DB says the new build shipped, the container keeps the old one), `runInTenant` enforced only at the Conductor's outer wrap while cron/GitLab-sync/RAG-write paths bypass it, unrestricted worker-container egress by default, a non-constant-time webhook auth path, and the audit log being deleted by the very workspace-deletion it should record. These were code-verified, not doc-inferred, but they warrant their own remediation track — and deploy rollback (A17) is explicitly gated on fixing the redeploy bug first.
- **"Solid at the core" rests on code reading, not a live end-to-end run of each module** — a few claims would benefit from the owner confirming behaviorally on a real device/account before treating as settled: the full autopilot chain end-to-end, iOS Safari PWA install/push behavior, and the redeploy-stale-code bug in particular.
- **Some edges may already be in flight.** Documents, Skills, and Designer-inspiration all landed 2026-07-16/17, so a handful of "missing" cross-links may be mid-build rather than truly absent — worth a quick confirm on the freshest modules before scheduling work against them.
- **Lighter-covered dimensions.** The scan is feature/coupling-focused; it did not deeply probe cost/€-budget behavior under real load, actual platform-API quota ceilings, or i18n/localization completeness of the newest modules — treat these as under-covered rather than clean.
- **Vision cases with no home in the code at all** (not just under-wired — entirely absent): **newsletter/email SEND** (copy is generated, but there is no subscriber list or send path anywhere — `@luckystack/email` is used only for auth email-change); **podcast / audio-only distribution** (voice + music are generated per piece, but no RSS/audiogram/audio publish target exists); and **subtitles / dubbing / localization** (no auto-caption track and no second-language voice pass, despite being named in `IDEA_TO_OUTCOME_PROGRAM.md`). Each is a genuinely-new build (proposed as A1, A19, A4), not a wiring fix.

## Appendix — per-dimension state (raw scanner assessments)

### dev-pipeline

The dev-pipeline engine is genuinely solid at its core: the Conductor is a real single-writer state machine (2775 lines, control-API dispatch, RBAC, blocks-gate, edit-lock, pause/resume/kill all wired end-to-end and reachable from the ticket-detail UI), stageRunner.ts actually drives a real interactive claude PTY inside a real container, captures the result off a Stop hook, persists CarryOver envelopes, advances tickets, fires CI gates on test stages, and pushes/opens MRs on approval. The stage editor (pipeline/page.tsx, 771 lines) is a rich, real UI covering system prompt, custom instructions, definition-of-done, custom statuses, context-doc/skill toggles, per-command allow/ask/deny, network policy, hooks, and model/effort/escalation rules, with durable create/save/reorder/delete via control-API syncs. Where it falls short is in the gap between what the stage editor lets you configure and what the runtime actually honors: per-stage network policy and the skill/MCP toggle are stored but not wired into the actual container launch or MCP config, WIP limits are enforced on the board but have no editor field, there is no persisted record of what an autonomous turn actually did (no per-tool-call audit trail, only an ephemeral live terminal broadcast), every workspace is seeded with the exact one hardcoded 7-stage pipeline with no alternative templates despite 'customizable pipelines' being the headline pitch, and the design corpus's own mandated first regression test (the golden-fixture renderer test) was never built.

### designer

The Designer module is genuinely one of the more mature areas of Workspaces: a full visual editor (Components/Styles/Animations/Themes/Typography) with live preview under an active theme, AI generation for themes/styles/animations via the pluggable provider layer, A/B compare between two saved themes, a curated "Gallery" of full theme+style+font+animation "looks," a library with import/export/copy, and a real coupling into the dev pipeline (active theme/style gets injected into every coding-agent stage via designSystemDoc.ts, ADR 0034). The "compare with online styles" half (INS, landed 2026-07-16/17) is real and working end-to-end: a throwaway chromium container screenshots any URL or accepts an uploaded screenshot, a vision model extracts a theme, and a side-by-side compare produces a markdown critique that lands in an existing UI-review inbox with a one-click "make ticket" action. However, this newest half is also the least finished part of the module: it only extracts color tokens (not the style/font/motion half of a "look"), has no discovery/search step (you must already have a URL), is desktop-viewport-only, requires manually typing your own site's URL despite the deploy system already knowing it, runs as a single blocking multi-minute request with no phone-friendly async/notify pattern, and hands the implementing agent a text URL rather than structured design data. These are finishing-touch gaps on a feature that landed very recently, not signs of a hollow module.

### interviewer-ideas

The standalone Interviewer (src/workspaces/interviewer/page.tsx + server/interviewer/{role,findings}.ts) is genuinely past the notification-only stub stage described in ADR 0034 — it now has: a free-form repo-aware chat (workspaces/aiChat → interpretChat, shared with the Assistant, RAG-grounded on code + product-knowledge, can itself propose create-ticket/create-content actions and multi-step plans); a structured 'Generate ideas now' path that parses AI markdown output into categorised, persisted `InterviewFinding` rows (area/severity/title/summary); a working finding→ticket conversion through the Conductor (B-23 compliant); and a generic cron/trigger wiring (server/automation/executor.ts + scheduled/page.tsx) so the interviewer can run unattended on a schedule and its output is recorded as real findings (not just a notification). What's still thin: the loop from 'AI notices something' to 'human sees it and acts, especially from a phone' has several real breaks — notifications produced by an interviewer run carry no navigable deep-link (push AND in-app), the manual-focus UI is desktop-only, findings have no dedup/history awareness so scheduled runs can pile up duplicates, the `detail` field meant to carry the AI's fuller reasoning is wired in the schema but never written or read, multi-project workspaces have no project attribution on a finding and 'make ticket' silently defaults to the oldest project, the ideation itself only reasons over code + product-capability text (never the workspace's own already-computed operational signals like cycle time or spend), and the on-demand run path executes the LLM call inline on the same single-writer chain that serialises every other write for that workspace, so a casual click can stall the whole team's board for up to three minutes. None of these are 'absent' — they are the finishing-touches and cross-module wiring that would turn a working structured-ideas feature into a trustworthy, always-on background analyst.

### video-marketing

The video/marketing render pipeline is far more mature than a typical prototype: server/content/render.ts is a genuinely deep ffmpeg wrapper with real multi-clip stitching (buildVideoStitchPlan), crossfade/xfade transitions, an audio mix engine (voice+ducked-music+sfx via amix), real timed captions (srt/vtt with ffprobe-anchored timing, burn/soft/sidecar modes), a CTA end-card overlay, a brand watermark pass, poster-frame extraction, last-frame continuity extraction for i2v, and webm/gif transcoding - all wired through assembly.ts into a live Prisma-backed pipeline with a real VideoTimelineEditor UI (scene reorder/split/trim/refine-by-range, waveform display, audio mix sliders, free client-side preview before paying for a render). Aspect-ratio presets (16:9/9:16/1:1) and reusable OutputTemplates (format+watermark) are built AND wired into the actual render call, contradicting the stale ADR note that called that wiring a 'follow-up'. What is genuinely missing or half-baked, verified against the code: (1) there is no custom-thumbnail upload path to YouTube/TikTok at all - the only 'thumbnail' is an auto-extracted video frame used solely as an in-app gallery preview; (2) the one 'thumbnail' generator that exists (Studio's marketer role) produces HTML ad creatives, not a raster image, and has no connection to content pieces; (3) still images are shown as static frames - the Ken-Burns/zoompan motion explicitly called for in the project's own IDEA_TO_OUTCOME_PROGRAM.md was never implemented, which is the literal 'slideshow' problem the scan brief asks about; (4) the 'fade' and 'xfade' transition options collapse to the identical ffmpeg effect; (5) burned captions have zero style/font/color/animation control; (6) the timeline editor explicitly defers drag interaction in favor of buttons/number-inputs; (7) there is no branded intro/outro clip concept; (8) no one-click multi-aspect batch export. None of these are fabricated - each was confirmed by reading the actual render/publish/UI source, not inferred from docs.

### content-automation

The content-automation/publishing pipeline is more built than a first pass suggests: PublishJob/Channel models, real YouTube resumable-upload + TikTok init/poll adapters, encrypted multi-account OAuth (per-platform, per-account token keys), token auto-refresh, scheduled ('park for later') posting fired by a leader-gated @luckystack/cron job every minute, audience-metrics ingest, and a genuine autopilot chain (idea -> piece -> pipeline -> publish, ADR 0269) that a channel can opt into. The backend logic for '10 channels on cron timers' is real, not a stub. However, verifying end-to-end from the UI surfaced that the single entry point for creating a cron job (the Scheduled-tasks page) cannot actually address a channel, so the autopilot chain is currently unreachable without hand-editing the database or the Assistant chat (which has trigger-save marked 'later' / not exposed either) - a load-bearing gap for the exact vision this dimension targets. On top of that, failure handling around publishing is the weakest link: failed scheduled/autopilot posts are silent (no notification, excluded from the one calendar view that exists), there is no retry mechanism (manual or automatic), the publish composer's account picker silently ignores the channel's configured default account, and there's no per-channel health view to sanity-check that N automated channels are actually still posting. These are finishing-touch-sized fixes on an otherwise solid foundation, not rebuilds.

### workspace-modules

Module-typing exists and mostly works: WORKSPACE_MODULES (development/content/design/documents, src/workspaces/_data/modules.ts) is a real, single-source-of-truth preset→section-list model consumed consistently by both the create flows (Onboarding.tsx for zero-workspace, CreateWorkspaceForm in Shell.tsx for N-th workspace) and by nav-gating (Shell.tsx, MobileChrome.tsx, WorkspacesShell.tsx all call isSectionEnabled/isModuleEnabled) and by page-level conditionals (settings DevOps tab, ticket-detail DevOps panel, designer Components section). Sections can be re-toggled after creation via workspace/page.tsx SectionsTab. This is genuinely solid plumbing. What's missing is everything AROUND that plumbing that would make 'spin up a workspace purely for X' actually smooth: there is no purpose-differentiated seeding (every workspace, content/design-only or not, gets the full 7-stage dev pipeline + git-workflow starter library seeded into the DB with zero UI surface to reach it), no tier/depth choice at creation despite a documented 3-tier preset system, no way to clone an existing workspace's config into a new purpose-specific one, and — most consequential for the phone-first goal — no way to create a second/third workspace at all from a phone once you already have one, since the entire workspace-switcher+create UI lives in a `hidden md:flex` desktop-only header.

### documents-builder

The Documents module (ADR 0271, landed 2026-07-16/17) is a real, working single-writer AI document library, not a stub: create/edit/delete, four AI draft modes (generate/rewrite/summarize/extend) grounded on the workspace's own other documents + product-knowledge RAG, apply/discard-draft as the B-23 consent step, AI image generation via the shared media pipeline, and a genuinely solid native export layer (md/html/xlsx built dependency-free, docx/pdf via throwaway Docker containers with brand-logo inlining) all work end-to-end and are wired into the Conductor + RBAC + RAG indexing correctly. What's thin is everything around that solid core: the module is an isolated island with no relation to tickets or decisions, no document typing/templates despite the spec calling for a `kind` field that never shipped, no wireframe/diagram capability despite that being named explicitly in the product vision, a version-history table that is written on every change but never read back anywhere in the UI, a dead `archived` schema field with no op or button to set it, no search across the document list or in the global command palette, no path to hand the AI an existing uploaded document to revise (uploads are opaque attachments only), and no diff view when reviewing a full-document AI rewrite before applying it. None of these are fabricated — each was verified against the shipped Prisma model, the Conductor's op switch, the sync route's allowed-op set, and the actual page/component files.

### skills-system

The universal Skill model (ADR 0270, landed 2026-07-17) genuinely works at its core: a workspace-scoped Prisma model with 5 builtin seeds (humanizer, tone-of-voice, seo-optimizer, brand-voice, jargon-translator), idempotent lazy-seeding, full CRUD via 4 RBAC-gated Conductor ops, and a single injection helper (skillPromptBlock) wired into BOTH real AI choke points — the one-shot completion registry (server/ai/registry.ts, covering every AiFeature with no bypasses found) and the PTY dev-pipeline stage-runner (as a contextDoc). This is backed by a solid, real integration test (tests/integration/skillsLayer.test.mts, 28 assertions) covering seeding, apply-point filtering, the four ops, builtin-protection, reset, and tenant isolation — not a stub. However the layer is young and thin at the edges: it has a settings-only UI with no visibility elsewhere in the app, no reachability from the Assistant chat (deliberately deferred via opCatalog mode:'later'), zero builtin content for the dev-pipeline (the one apply-point group the injection wiring was built to reach has no seeded skill that ever populates it), no per-stage granularity, no shared picker-UI shell (was scoped in the build plan, not delivered), and it coexists confusingly with an older, unrelated 'skill' concept (InfoSource mode='skill') used by the Sources page and the pipeline stage's own 'Skills/MCP' picker. In short: the injection mechanism is real and correctly wired; the surrounding product experience (discoverability, phone-first control, dev-pipeline default value, cross-workspace reuse) is where the gaps are.

### mobile-pwa-ux

Phone-first PWA plumbing itself is genuinely solid: a real manifest.webmanifest + dependency-free sw.js (push + notificationclick deep-link), env-VAPID push wired into every server-side notify site (assignment/automation/aiSuggestion), per-category opt-out prefs, a beforeinstallprompt-based install flow, and dedicated mobile chrome (MobileChrome.tsx: slide-in nav drawer, notification sheet, workspace switcher) plus isMobile-aware board/backlog/content pages and a phone-usable structured approve/answer card (NeedsInputBanner) — this is not a stub, it's built and largely working. The gaps are concentrated at the edges of that solid core: (1) the write path is fire-and-forget with no visible offline/reconnect state, which is a real risk to the core 'approve from your phone' promise; (2) the install/push story silently breaks on iOS Safari with zero fallback UX or error messaging, a big blind spot given iPhone's share of phone users; (3) several finishing-touch issues (sub-16px input font sizes causing iOS auto-zoom, sub-44px touch targets in dense controls) work against the 'simple UI' mandate; and (4) a handful of modules — Terminals' lack of a mobile key toolbar, the Knowledge graph's untappable nodes at phone scale, and Designer/Studio/MR-review having no mobile layout pass at all — were evidently built desktop-first and never revisited for phone, despite Designer/Studio being explicitly named in the product vision as things a phone-first user should be able to use.

### assistant-rag-ai

The AI/RAG/provider backbone is the most mature dimension in the codebase: a genuinely generic provider registry (server/ai/registry.ts) with a real per-feature, per-workspace override seam that has a working settings UI (workspace/page.tsx PROVIDER_OPTIONS + provider-health chips, both actually wired to EnvVar-backed overrides, not just exported-for-a-UI-that-never-came); a single retry policy at the one choke-point; a universal Skills-injection layer (server/ai/skills.ts) that reaches every feature through the same choke-point; and a unified RAG store (RagEntry) shared cleanly across four corpora (code, product-knowledge, institutional-memory, content-playbook) via one retrieve()/embedTexts() pair with a real Gemini-or-deterministic-local embedder fallback and spend metering. Product self-awareness (retrieveProductKnowledge) is now wired into the Assistant chat, Interviewer, MR-review, Studio, Documents, and the stage-runner — broader than the product map's own notes suggested, so that specific coupling gap is largely closed. What remains genuinely thin, verified by reading the actual code rather than the docs: (1) the claude-cli provider — the one path nearly every reasoning feature rides — has no concurrency control and drives its PTY turn with blind fixed-timing sleeps rather than readiness detection, both real reliability risks given the product's own cron/automation ambitions; (2) the prompt-quality measurement loop (live golden evals, A/B PromptVersion, LLM-judge, reject-as-feedback) is fully designed in AI_QUALITY_AND_EVALS.md but has zero implementation beyond the free structural replay scorer; (3) institutional memory, despite being architected as a shared cross-cutting capability, is consumed by exactly one of five eligible reasoning roles; (4) the root-cause role reasons over MR titles alone with no diff or RAG grounding, unlike its sibling mr-review role. None of these are stubs in the sense of 'returns fake data' — they are real, working, but load-bearing gaps in the AI backbone every module depends on.

### coupling-integration

Cross-module coupling in Workspaces is a mix of genuinely well-built bridges and clear gaps, and it skews more complete than the product map suggested for several items I re-verified. Resolved/working (do NOT re-report): the product-knowledge RAG corpus is centrally wired into workspace-chat, interviewer, studio, MR-review, and documents (all via `retrieveProductKnowledge`), and MR-review effectively gets ADR grounding through it since ADR summaries are baked into that same corpus; the universal Skills injection layer is centralized at the single `runAiCompletion` choke point with a TS-exhaustive `AiFeature -> SkillApplyPoint` map, so coverage across every AI surface (content, designer, documents, interviewer, MR-review) is already enforced by the type system, not a risk; interviewer findings already flow into real tickets (`fireEvent('ticket.created', ...)` from a finding, conductor.ts line 2707); Designer's UI-review inbox already has a working 'make ticket' action (`ui-review-to-ticket` in conductor.ts); and the content channel-aware ideator (`recentWinnersLine`, per-channel `brandContext`/`brandMemory`) is fully built, contrary to the map's characterization of it as still-partial. The real gaps cluster around newer/adjacent modules that shipped without their natural cross-links: Documents (landed 2026-07-16/17) grounds only on itself + the static product-knowledge corpus, never on live tickets/decisions or existing Designer/Studio/Content media assets, undercutting its stated purpose as a technical-design-doc hub; Designer's inspiration-import and saved-theme library do zero RAG indexing, so theme generation never learns from what the workspace has already captured or made; Marketing's social-calendar output has no `channelId` and never touches the real publishing pipeline, making it a disconnected planning artifact; the deploy pipeline has no event that a demo-video capture (or any other automation) can hook into, and Studio/Designer landing artifacts have no path to actually go live despite mature deploy/DNS infra; the knowledge graph's own code comments admit it hasn't modeled the content-piece-to-ticket link and its node types haven't been extended for Documents/Designer; and the newly-landed comment inbox is read-only with no bridge into the ideator's already-built per-channel feedback slot.

### greenfield-adjacent

The content platform covers script to media to assemble to publish solidly for two platforms (YouTube, TikTok) with real generation (fal/ffmpeg/suno/elevenlabs) and a working analytics/insights page (content/insights/page.tsx: stage funnel, cost-by-feature, shortlink click-through with an A/B 'winner' badge, brand-voice editor). But most genuinely NEW adjacent modules named in the product vision are either entirely absent (podcast/audio distribution, subtitles/dubbing/localization, SEO metadata, a real newsletter/email-send capability, a workspace-wide asset library) or exist only as typed placeholders or one-shot utilities that were deliberately left unbuilt (Instagram/LinkedIn are in the PublishPlatform union but explicitly gated out of the UI per code comment '#147'; the web-scraper role is a single fetch-and-summarize for outreach leads, not a time-series competitor-watch surface; publish metrics overwrite a single snapshot with no history table, so there's no trend chart despite the raw counters already being pulled). Studio's 'email' artifact kind and 'thumbnail' artifact kind are both genuine dead ends: email produces marketing copy with zero send/subscriber-list plumbing anywhere in the codebase (grep for @luckystack/email usage outside the auth email-change flow returns nothing), and 'thumbnail' renders as an HTML/CSS mockup in an iframe, it never becomes a raster image, and no publish call anywhere sets a custom thumbnail on YouTube or TikTok. These are concrete, verified gaps, not speculation, each was grep-verified against the real server/ and src/workspaces/ trees rather than inferred from docs.

### security-ops

Security & operability is a mix of genuinely solid, invariant-enforced controls and real production-grade gaps hiding behind a mature-looking surface. What works well and is verified in code: the B-28 RBAC capability matrix (hasCapability/CAP, every _api route rate-limited 48/48), the ADR-0266 hardening sweep (owner-protection, capability-ceiling on role-create, redacted push, SSRF-blocked webhook trigger targets, prod-deploy-bypass closed, git token off argv), fail-closed at-rest secret encryption (secretBox.ts throws rather than ever storing plaintext), a host-wide EUR spend ceiling (WS_HOST_SPEND_CAP_EUR) actually wired into both spend/record.ts and media/budget.ts, a real HMAC-verified + origin-exempt forge webhook endpoint that is secure-by-default (503 when no secret configured), and an append-only governance AuditLog. But several load-bearing claims don't fully hold up under inspection: the deploy/promote/redeploy path has a container-reuse bug that means redeploying an already-deployed environment never actually pulls new code (the DB says the new build shipped; the container silently keeps serving the old one) with no rollback/history to fall back on either way; the `runInTenant` tenant-isolation invariant that the project treats as non-negotiable is in practice only enforced at the Conductor's single outer wrap, while cron/trigger execution, GitLab issue sync, and most of the RAG/self-knowledge write paths bypass it entirely in favor of manually-threaded workspaceId filters (correct today, but they've opted out of the loud-fail safety net the architecture doc promises); worker-container egress is unrestricted by default despite the product's core loop being 'let an AI agent run code in this container'; one webhook auth path isn't constant-time; the audit log doesn't survive the deletion it's supposed to record; and destructive-action confirm dialogs — the human-approval choke point the whole single-writer model rests on — have almost no accessibility support.
