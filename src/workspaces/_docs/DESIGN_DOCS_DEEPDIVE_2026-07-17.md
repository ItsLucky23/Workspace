# Design & Document tools — Deep Dive (2026-07-17)

Two tools, two very different distances from the owner's vision. The **Design tool** is a mature token-and-inspiration studio — AI theme/style/animation generation, live gallery previews, and a working screenshot/URL critique flow — but it has no path from a design to *applied UI*: "build a UI from 0" has no end-to-end home anywhere (greenfield scaffolding is 100% non-generative, and Studio's generated HTML can't be written into a repo), and the "decent → premium" loop is lossy at every seam — inspiration import keeps color only, compare produces prose with no rendered before/after, capture is desktop-only, and every structured design artifact is stripped or dropped before the coding agent sees it. The single biggest thing between today and the Design vision is that **nothing structured survives into real applied UI**; the highest-leverage first move is making inspiration extract the full premium dimension-set (spacing/type/shadow/motion), not just 30 colors.

The **Document tool** has a genuinely solid generation-review-export core (four AI draft modes, single-writer consent, a wired humanizer, five export formats) — but its headline journey, "upload school PDFs → a submission-grade technical design doc," is **not reachable today**: the upload silently fails before it starts (the client rejects the PDF extension), and even once unblocked there is zero text-extraction code anywhere in the repo, so a PDF's content never reaches a prompt. The single biggest thing for the Document vision is the **missing ingestion spine** (unblock upload → extract → store → ground); a close second is that wireframes and diagrams can't render in any surface — editor, review, or export — which is exactly what makes a design doc *look* like a design doc. Net: the Document tool needs one spine built to become *possible*, the Design tool needs its lossy seams closed to become *premium* — and several of the biggest fixes (a file parser, a diagram renderer, background-job+notify, a phone diff viewer) are **shared infrastructure worth building once**.

## Design tool — deep dive

### Where it stands today

**J-D1 (UI from 0):** There is effectively **no** design-from-zero path. The only "start from nothing" flow in the whole product is `project-from-template` (ADR 0046): `server/scaffold/templates.ts` ships exactly 4 hardcoded stack skeletons, and the react-vite template's *entire* UI is `function App(){ return <h1>Hello from Workspaces</h1> }`. The "Create Project" form (`Shell.tsx` `CreateProjectForm`) collects only a `name` + `template` picker — there is **no brief/description field anywhere**, and `initGreenfieldRepo` (conductor.ts) just writes the static `StarterFile[]` to git with zero AI calls. The nearest generative surface is Studio's `landing`/`component` kinds, which *do* turn a brief into visual markup — but they emit one sealed self-contained HTML blob (inline CSS, no JS, no multi-page, no IA), stored verbatim as `StudioArtifact.content.html` and rendered only in an iframe, with **no write path into a repo**. The Designer's own theme/style/animation generators work well from a brief, but produce tokens, not pages, and nothing composes an applied look into an actual layout — so "describe an app → get a real starting UI" is unsupported end-to-end.

**J-D2 (decent → premium):** The module is genuinely mature — visual token editor, AI theme/style/animation generation, gallery live-previews, A/B compare of two saved themes, and an inspiration/compare flow (landed 2026-07-16/17) that injects the active theme into coding stages via `designSystemDoc.ts` (ADR 0034). But the "elevate" loop is lossy at every seam that matters. Inspiration import extracts **color tokens only** — the exact dimensions J-D2 defines as "premium" (radius, shadow, border, density, font pairing, weight, tracking, motion) are asked-for-nowhere and dropped, even though the full `DesignStyle`/`AnimSpec` schema already exists in `generateAsset.ts`. Compare produces **prose only** (stored in `UiReviewRequest.notes`) — there is no rendered before/after anywhere. Capture is **desktop-only** (hardcoded `1440x2200`), so the phone form factor the journey targets is literally never seen. And the handoff into the coding pipeline strips or omits every structured design artifact, so the implementing agent re-imagines premium-ness from a sentence.

### Gaps & build proposals

#### J-D1 — UI from zero

**1. Greenfield scaffold is 100% non-generative** *(new; most concrete confirmation of the "no home" verdict)*
- *Missing:* No brief reaches the scaffold step; every react-vite project gets the identical one-line Hello World regardless of what it's for. No AI call exists in this path.
- *Blocks:* The core J-D1 promise ("describe an app → real starting UI") is impossible at project-creation time.
- *Proposal:* Add an optional `brief` to `project-from-template`'s wire shape + `CreateProjectForm`. When present, seed an `APP_BRIEF.md` InfoSource (reuse the existing `starterDocs → InfoSource` path in `templates.ts`) and auto-file a first-class "scaffold the app" ticket into the default pipeline whose refine/plan/impl stages consume it — reuses the ticket→stage→agent machinery, no new verb (invariant #2, B-23).
- *Impact:* high · *Effort:* M

**2. Studio's `landing`/`component` generators are sealed off from the product** *(new)*
- *Missing:* The one surface that turns a brief into visual markup is capped at a single self-contained HTML fragment, no multi-page/IA, and has zero repo-write path — it never becomes a React component, route, or `page.tsx`.
- *Blocks:* Can't satisfy "produce a real, usable UI (layout + components + pages)."
- *Proposal:* (a) Give Studio artifacts a repo-write path — turn "apply this artifact" into a ticket whose impl-stage agent receives the HTML as a reference and re-implements it as real React components + a route (same screenshot+prose→ticket handoff already used for redesigns); **or** (b) build an "app scaffold" generator that outputs a *structured* IA spec (route list + per-page component list + one-line purpose) and files it as a ticket **batch** (one ticket per page) — structure, not a single opaque HTML blob.
- *Impact:* high · *Effort:* L

**3. The tokens→page seam is invisible — no "now build a page" CTA** *(new; deepens the "tokens aren't UI" observation)*
- *Missing:* After generating a beautiful theme+style, there is no in-Designer action that produces a page. The Designer→pipeline bridge (`designSystemDoc.ts`) exists but is never surfaced as an actionable button; the user must already know the board exists.
- *Blocks:* J-D1's from-scratch case stalls at "tokens set, now what?"
- *Proposal:* Add a single **"Scaffold a page with this look"** CTA on the Gallery/Themes screen (once a look is active) that files a ticket pre-populated with active theme/style/animation ids + a brief textarea, via the existing ticket-creation control-API op — makes the hidden ADR-0034 bridge discoverable.
- *Impact:* medium · *Effort:* S

#### J-D2 — decent → premium

**4. Inspiration extraction is color-only** *(supersedes prior "extracts color tokens only"; deepened with the exact reusable schema + save path)*
- *Missing:* `EXTRACT_SYSTEM` (`inspiration.ts:45-50`) requests only `{name, description, light, dark}`; `saveThemeProposal` writes only a `kind:'theme'` artifact. Radius/shadow/border/density/font/weight/tracking/motion — the precise "premium" dimensions — are never asked for, though `buildStylePrompt`/`buildAnimPrompt` (`generateAsset.ts:12-24`) already define validated schemas and `coerceStyle()` (`styles.ts`) already fills gaps.
- *Blocks:* This is the **single highest-leverage fix** — an import that keeps only hex just recolors the existing look and can never resemble the reference.
- *Proposal:* Extend extraction to also request a `DesignStyle` (and optional `AnimSpec`) JSON from the same screenshot — reuse `buildStylePrompt`'s schema string + `parseAsset`/`coerceStyle`, and add `saveStyleProposal`/`saveAnimationProposal` mirroring `saveThemeProposal` (`saveDesignArtifact` in `library.ts` is already kind-agnostic). Prefer **one combined vision call** returning theme+style+animation (cheaper, same request); user reviews/activates each independently.
- *Impact:* high · *Effort:* M

**5. Compare produces prose only — no rendered before/after** *(supersedes prior; merges three new findings on the same gap)*
- *Missing:* `compareDesigns` stores a markdown verdict in `UiReviewRequest.notes` (8000-char slice); nothing renders a candidate "after." There is no after-render primitive in the flow even though `Gallery.tsx`'s `LookPreview` already renders any `{theme, style}` pair live via CSS variables onto real demo surfaces.
- *Blocks:* J-D2 explicitly requires before/after; today the only artifact is a paragraph the user must mentally translate — nothing to approve or show a stakeholder from a phone.
- *Proposal:* Two independently buildable pieces: (a) once #4 lands and extraction yields a theme+style pair, feed it straight into `LookPreview` to render an "after" thumbnail inline in the UiReviewForm/inbox next to the "before" screenshot — no new render engine; (b) for a true page-level after, apply the candidate theme's CSS vars via an `--inject-css`/query-param override on a re-capture of the *same* page (reuse `captureUrlScreenshot`'s chromium pipeline) to produce a genuine before/after pair attached to the `UiReviewRequest`.
- *Impact:* high · *Effort:* M (thumbnail) / L (page-level after-render)

**6. Capture + compare are desktop-only** *(supersedes prior; tied to the phone journey)*
- *Missing:* `captureUrlScreenshot` hardcodes `--window-size=1440,2200`; no mobile viewport exists anywhere (grep confirms zero other sizes).
- *Blocks:* The journey requires premium fidelity judged on a phone — mobile nav collapse, touch targets, and mobile type scale are exactly what separate decent-on-desktop from premium-on-phone, and are never captured. A redesign ticket built from a desktop-only critique can regress mobile.
- *Proposal:* Add a `viewport: 'desktop' | 'mobile'` param (second `--window-size=390,844` invocation, same container/`persistMediaBytes` path); have inspire-url/compare optionally capture both and add a `COMPARE_SYSTEM` bullet calling out per-breakpoint hierarchy/spacing/touch-target differences when a mobile pair is present.
- *Impact:* high · *Effort:* M

**7. Blocking ~3-min capture with no queue/progress/notify** *(deepens prior; names the existing pattern to copy)*
- *Missing:* `InspirationForm` awaits the full round trip synchronously (`timeoutMs:180_000` inline in the request cycle); nothing is queued or broadcast, and the tab must stay open. The exact solution already ships in `server/content/queuedMediaJob.ts` (`runQueuedMediaAsset`: queued row up front + live delta at each transition).
- *Blocks:* Background/notify for long jobs is a named target capability; on a phone, backgrounding or a flaky connection silently loses the whole capture with no record.
- *Proposal:* Convert inspire-url/inspire-image/compare to the `runQueuedMediaAsset` shape — create a lightweight queued row immediately, run capture+extract in the background, broadcast a workspace-room delta (reuse `broadcastContentAssetDelta`), and fire a `PushNotification` (`server/hooks/webPush.ts`) when the proposal is ready.
- *Impact:* high · *Effort:* M

**8. No web-discovery — user must already have a reference URL** *(confirms prior; flags it needs genuinely new infra)*
- *Missing:* `inspire-url` requires a typed `http(s)` URL; the only other web-fetch feature (`scraper`) also needs a pre-set URL. No web-search provider is wired anywhere in the AI layer (grep confirms).
- *Blocks:* Finding a good reference is part of the creative task; today the user must leave the product to search and paste a URL back.
- *Proposal:* Per Rule 12a/3b — **flag before hand-rolling**: this needs a new search-capable provider. Add a `designer-discover` AiFeature (mirrors the per-feature registry in `server/ai/types.ts` + `assignments.ts`) backed by a search-augmented provider (Gemini-with-search or a dedicated search key) that returns candidate URLs + one-line rationale for a typed brief, feeding straight into the existing `inspire-url` op.
- *Impact:* medium · *Effort:* L

**9. No component-level compare** *(supersedes prior; adds the prompt-vs-input mismatch)*
- *Missing:* `COMPARE_SYSTEM` explicitly asks the model to compare buttons/cards/inputs, but it only ever receives two full-page 1440×2200 screenshots — no crop, region-select, or component-isolation step exists in `InspirationForm` or the API.
- *Blocks:* Premium work lives disproportionately in component detail; forcing the vision model to guess which pixels are "the button" yields vague, less-actionable critique than the prompt's own ambition.
- *Proposal:* Add a lightweight client-side crop before either side is sent (canvas rectangle-select over the captured/uploaded screenshot, reusing the `MediaUploadButton` pipeline for the cropped result) — **or** a headless-chromium clip-region capture scoped to a CSS selector — so "apply to ours" bullets ground on the actual button/card pixels.
- *Impact:* medium · *Effort:* M

**10. Density is one global enum — no targeted per-section fix** *(new; structural ceiling)*
- *Missing:* Density (`styles.ts`) is a 3-value enum applied workspace-wide via a single CSS-var block; no per-component/per-region override. A critique like "the pricing cards are too cramped, the hero has too much air" cannot be represented as a Designer-side change at all.
- *Blocks:* Caps what the Designer can "elevate" to uniform global knob-turning; real hierarchy/spacing fixes get pushed to the coding pipeline as unstructured prose.
- *Proposal:* **Flag as a structural ceiling, not a quick fix.** If pursued: extend `DesignStyle` with named overrides keyed to component categories the system already knows (card/button/nav — the surfaces `LookPreview` already renders), so a scoped critique can set a scoped override.
- *Impact:* medium · *Effort:* L

**11. Own-page URL isn't autofilled from the deployed Environment; no re-check loop** *(supersedes prior #19; adds the closed-loop gap)*
- *Missing:* `ownUrl` is a bare text input retyped every time, even though the live URL is a known structured value (`Environment.route`, `schema.prisma:391`). Once a compare becomes a ticket (status→`ticketed`, terminal), nothing re-captures the same URL after the redesign ships.
- *Blocks:* Both hit J-D2's "let the user iterate" — retyping a URL is phone friction, and there's no way to confirm the elevation worked without redoing the whole flow.
- *Proposal:* (a) Prefill/offer the workspace's `Environment.route` as a one-tap option next to `ownUrl` (one-line query in the compare op); (b) add a **"Re-check"** action on a `ticketed` `UiReviewRequest` that re-runs `captureUrlScreenshot(ownUrl)` + a fresh compare against the same inspiration and appends the result to the same request — closing the before/after loop.
- *Impact:* medium · *Effort:* S

#### Apply-and-iterate handoff (J-D2 → coding pipeline)

**12. Redesign tickets carry raw screenshot + prose, never the structured artifact** *(supersedes prior #20; merges two new findings)*
- *Missing:* `ui-review-to-ticket` (`conductor.ts:2559-2585`) builds the ticket description from `review.problems`/`notes`/screenshot URLs only, creates **no** `TicketArtifactLink`, and never references any `DesignArtifact` — even when the same inspiration session already produced a saved theme/style proposal. The compare and extract paths leave disjoint trails.
- *Blocks:* Even after #4 produces a proper theme+style, the implementing agent sees only a URL (possibly un-fetchable) + English prose, re-deriving spacing/radius/motion in its head — the exact "lossy handoff" the journey flags.
- *Proposal:* When `ui-review-to-ticket` fires for a compare, persist the extracted style/theme as an inactive `DesignArtifact` (`saveDesignArtifact`) and either reference it by name in the description ("Apply the saved look `<name>` — see `namedLooksCatalog`") so the agent resolves it through the **existing** named-look mechanism (`designSystemDoc.ts:50-73`), and/or auto-create a `TicketArtifactLink` (reuse `ticketArtifact_server_v1.ts`).
- *Impact:* high · *Effort:* M

**13. Linked Studio HTML is stripped before the coding agent sees it** *(new)*
- *Missing:* `artifactContext.ts::renderStudio` replaces a linked `landing`/`component`/`thumbnail` artifact's real HTML+CSS with a fixed placeholder ("HTML omitted here; match its structure"). This is the only artifact type that could carry a rendered, component-level premium reference, discarded exactly at the agent handoff.
- *Blocks:* The one mechanism that could deliver a concrete rendered reference is thrown away, forcing the agent to re-imagine premium-ness from a sentence.
- *Proposal:* In `renderStudio`, for kinds with `content.html`, inline a bounded/sanitized excerpt (first ~4-6kb, matching the `renderStage.ts` docs-truncation pattern) instead of the placeholder; keep the placeholder only as a fallback when `content.html` is absent.
- *Impact:* high · *Effort:* S

**14. Linking an `animation` artifact transfers zero motion data** *(new)*
- *Missing:* `artifactContext.ts` routes any non-`theme` `DesignArtifact` through `buildDesignSystemDoc(null, meta)` (the *style* branch), which reads radius/density/shadow/font — none of which overlap an `AnimSpec`'s `{fade,x,y,scale,rotate,easing,duration,bounce}`. The rendered block becomes just a heading + description.
- *Blocks:* Motion is a named premium dimension; a linked entrance animation silently loses its duration/easing/offsets — invisible data loss in the one path meant to carry exactly it.
- *Proposal:* Branch the `DesignArtifact` handling on actual `kind` (theme | style | animation) and add a small animation renderer ("Entrance — fade:{fade}, offset:({x},{y}), scale:{scale}, easing:{easing}, duration:{duration}s") instead of collapsing style+animation into one ternary.
- *Impact:* medium · *Effort:* S

**15. No fast/lightweight "apply theme" path — every application is a full pipeline run or a manual clipboard paste** *(new)*
- *Missing:* `setActiveDesignArtifact`/`saveDesignArtifact` only rebuild the passive `design-system` InfoSource doc read at the *next* stage spawn — nothing writes `src/index.css`. Landing tokens live means either (a) file a ticket that runs the entire refine→plan→impl→test→review pipeline (redesign tickets start at `stageId:'unrefined'`, same weight as a new feature), or (b) "Export" → clipboard → manual paste (bypasses Conductor/consent/mobile-review).
- *Blocks:* J-D2's "tightness of the see-change→approve→apply loop" — a purely mechanical token substitution costs a full agentic run or an ungoverned, non-phone copy-paste. Neither lets someone iterate quickly from a phone.
- *Proposal:* Add a narrow **`apply-active-design-tokens`** control op (through the single-writer Conductor, B-23) that deterministically rewrites the `@theme` block in `src/index.css` from the active `DesignArtifact` rows and commits directly — no agent turn needed (the transform is a token-name→CSS-var map; `themeToCss` already exists client-side in `themes.ts` and can be ported server-side). Reserve the full pipeline for redesigns that also touch layout/markup.
- *Impact:* high · *Effort:* M

**16. No after-screenshot verification once a redesign ticket completes** *(new; complements #5/#11)*
- *Missing:* `captureUrlScreenshot` is called only from the two inspiration ops; nothing re-captures after a redesign pipeline finishes, so there's no automated "after" next to the original "before."
- *Blocks:* J-D2 requires before/after; today the approver must manually open the live app on a phone, with no durable record next to the request.
- *Proposal:* On the final gated stage of a `ui-review`-labeled ticket (or any ticket with a linked design artifact), reuse `captureUrlScreenshot` against the ticket's environment/preview URL and attach the result to the originating `UiReviewRequest` as an "after," rendered beside the "before." (Overlaps #11's Re-check; build once.)
- *Impact:* medium · *Effort:* M

#### Cross-cutting

**17. No N-variant generation — every Designer AI call yields exactly one proposal** *(new)*
- *Missing:* `runAi` calls `generateTheme`/`generateStyle`/`generateAnimation` with a single prompt → one saved proposal; no `count`/`variants` param anywhere. The existing "A/B compare" only diffs two artifacts produced in separate serial calls.
- *Blocks:* The journey explicitly asks about "variant generation + pick"; exploring a look today means manually re-running the prompt N times and eyeballing a list — the natural way to explore serves *both* J-D1 (from-scratch directions) and J-D2 (premium pass).
- *Proposal:* Add a `count` (1-3) to the generators, fire N parallel calls with slight prompt/temperature variation, return an array of *unsaved* proposals, and render them side-by-side in the existing `Gallery.tsx` `LookPreview` for one-click "use this one" — no new preview chrome.
- *Impact:* medium · *Effort:* M

**18. Component-level premium work has no home on either side of the loop** *(new; ties #9 + #13 together)*
- *Missing:* Studio's `component` kind is a generic marketing brief with no way to target a *specific existing* product component; compare is whole-page desktop-only; and even a generated Studio component has its HTML stripped (#13). So there's no path from "this exact dropdown is decent" to a targeted premium reference for it.
- *Blocks:* The journey calls out "component-level vs whole-page work"; the entire loop operates only at whole-app-theme or whole-marketing-component grain.
- *Proposal:* Extend compare to optionally take an element/selector scope (clip-region headless-chromium capture, #9) paired with a Studio `component` brief **seeded from the actual component's current markup** (read from the repo) rather than a generic marketing brief.
- *Impact:* medium · *Effort:* L

**19. Saved themes/styles + past compare critiques are never RAG-indexed** *(supersedes prior #21; names the copy-paste-ready module)*
- *Missing:* `generateTheme`/`generateStyle` build prompts from the brief alone — no retrieval of the workspace's own saved `DesignArtifact` rows or past `compareDesigns` critiques. `server/content/referenceLibrary.ts` already implements exactly this shape (`addReference`→`embedTexts`→`RagEntry` under a reserved commit; `retrieveReferences`→`retrieve`), and `RESERVED_CORPUS_COMMITS` (`rag/index.ts:81`) *explicitly names "the inspiration library"* as a reserved-but-unwritten slot.
- *Blocks:* Every generation starts from zero — can't ground a new brief in "the fintech look you saved last month" or in what a past compare already flagged. Cheapest of the gaps (retrieval infra is a copy-paste of a shipped module).
- *Proposal:* Add `server/designer/designMemory.ts` mirroring `referenceLibrary.ts`: index each saved/active `DesignArtifact`'s name+description+key style bits and each compare critique into `RagEntry` under a new reserved `design-library` commit; call `retrieve()` from the three generator prompt-builders.
- *Impact:* medium · *Effort:* S

### Suggested build order for the Design tool

1. **#4 — extract style+animation (not just color)** — the single highest-leverage fix; every downstream J-D2 improvement (rendered after, structured handoff, apply) depends on there being a full artifact to carry.

3. **#12 — link the structured artifact into redesign tickets** (via the existing named-look/`TicketArtifactLink` mechanism) — completes the lossless apply-and-iterate handoff with #4/#13.
4. **#5 — rendered before/after** (thumbnail via `LookPreview` first, then page-level after-render) — makes the loop phone-reviewable, satisfies J-D2's explicit before/after requirement.
5. **#15 — the fast `apply-active-design-tokens` control op** — makes the see→approve→apply loop tight for pure token changes; pairs naturally with #16 re-check.
6. **#6 + #7 — mobile viewport + queued/notify capture** — makes the flow honest about the phone form factor and safe to run in the background.
7. **#1 + #3 — the J-D1 brief field + "Scaffold a page with this look" CTA** — opens a real (indirect) design-from-zero path reusing the ticket machinery; #2 (Studio→repo scaffold) is the larger follow-on.
8. **#19 — RAG-index the design library** — cheap grounding win once artifacts are richer (do after #4 so there's real style data to index).
9. **#17 — N-variant generation**, then the structural/exploratory items **#9/#18 (component-level)**, **#11/#16 (re-check loop)**, **#8 (web discovery)**, and finally **#10 (per-section density — flagged as a structural ceiling, scope explicitly before building).**

## Document tool — deep dive

### Where it stands today

**J-Doc1 (upload school PDFs → detailed technical design doc):** Effectively blocked at step one, and the block is deeper than the prior scan reported ("uploaded Word/PDF is an opaque attachment"). It's worse: the upload doesn't even complete. The editor's upload button advertises `accept="image/*,application/pdf"`, but the shared `uploadMedia()` helper's `ALLOWED` set has no `pdf` entry, so it returns `null` before ever calling `fetch` — `onUploaded` never fires and the spinner just clears with zero error feedback (the server route's `ALLOWED_EXT` would 415 it anyway). Even after that two-map fix, the PDF lands in `MEDIA_DIR` as inert bytes: repo-wide grep for `pdf-parse|pdfjs|mammoth|pdftotext` returns zero non-`node_modules` hits, `package.json` has no such dependency, and ADR 0107 / `15_SOURCES_MANAGEMENT.md` confirm extraction was deliberately deferred out of v1. `runDocumentAi` never sees a single character of the assignment brief or rubric. There is also no `kind`/template, so even a working generate run reinvents document structure from a one-line freeform instruction. This journey is **not reachable today**.

**J-Doc2 (submission-grade output):** The generation-and-review core is real and solid — 4 draft modes (generate/rewrite/summarize/extend) grounded on other docs + product-knowledge RAG, single-writer apply/discard consent, and a genuinely good multi-format export (md/html/xlsx dependency-free; docx via real pandoc and pdf via headless chromium in throwaway `--network none` containers, with brand-logo inlining). The humanizer is confirmed wired end-to-end through the shared completion choke-point with the ADR-0015 integrity boundary. But "submission-grade" leaks at every finishing edge: **wireframes/diagrams cannot render anywhere** (editor preview, AI-draft panel, or any of the 5 export formats); images/assets are a disconnected side-strip never embedded in `content` or exports; pdf/html silently garble links, fenced code, and footnotes that docx preserves; pdf has no page numbers or TOC; docx carries zero brand identity; there is no citation model; and reviewing a long AI redraft on a phone means reading the whole new doc in a 288px scroll box with **no diff**. Revision history is snapshotted but never listable or restorable. The scaffolding is premium; the last mile is not.

### The critical path for "upload school PDFs → technical design doc"

| # | Step | State | Note |
|---|---|---|---|
| 1 | User picks PDF in the editor upload button | **partial** | UI accepts `application/pdf` but `uploadMedia()` rejects the `pdf` ext client-side and returns `null` before fetch (`uploadMedia.ts:11-17,22-23`) |
| 2 | File uploads + lands in `MEDIA_DIR` | **partial → have** | Server `ALLOWED_EXT` also lacks pdf/docx (415); once both maps get `pdf`/`docx`, the existing `persistMediaBytes` binary pipeline handles it unchanged |
| 3 | Asset recorded on `Document.assets` | **have** | `addAssetUrl` stores `{kind,url,label}` |
| 4 | Extract text from PDF / docx | **must-build** | No extractor exists anywhere in repo |
| 5 | Store the extracted text durably | **must-build** | `assets` Json has no `extractedText`/`extractStatus` slot |
| 6 | Chunk + embed source text into RAG | **partial** | `indexDocument`/`chunkDocument` only ever touch `doc.content`, never assets |
| 7 | `runDocumentAi` actually retrieves the brief/rubric | **must-build** | Own-doc filter (`docs.ts:71`) would exclude asset chunks; top-k (k=4, 2500 chars) is far too thin to read a full rubric |
| 8 | Generate with a technical-design structure | **partial** | `generate` mode exists but there's no `kind`/template skeleton and it's a single blind completion, not outline-then-sections |
| 9 | Render wireframes / architecture diagrams | **must-build** | No mermaid/image rendering in editor, preview, or export |
| 10 | Review the draft on a phone | **partial** | Draft panel renders raw markdown with no diff vs current content |
| 11 | Export a submission-grade file | **partial** | Export works but drops images/links/code, lacks page numbers/TOC/citations, docx unbranded |

The five **must-build** steps (4, 5, 7, 9 + the step-1/2 unblock) are the spine of J-Doc1; steps 8–11 are the J-Doc2 quality layer that J-Doc1's "detailed" bar also depends on.

### Gaps & build proposals

#### PDF ingestion (the J-Doc1 spine)

- **Unblock upload (S, high).** Add `pdf`→`file` and `docx`→`file`/`doc` to BOTH `uploadMedia.ts` (`MIME_EXT`/`ALLOWED`) and `server/media/uploadRoute.ts` (`ALLOWED_EXT`). Pure two-map edit reusing `persistMediaBytes` — no route, no schema change. Without this the UI's advertised PDF support is a silent lie.
- **Add a text extractor (M, high).** New `server/documents/ingest.ts` reusing the proven `containerRender`/`docker(['run','--rm','--network','none','-v',…])` pattern from `export.ts:213-227`: a small poppler-utils image running `pdftotext -layout` for PDF, and the **already-pulled** `PANDOC_IMAGE` in reverse (`pandoc -f docx -t plain`) for Word — so docx needs zero new images and PDF needs one small one. Run it as a background step after `addAssetUrl`.
- **Give extracted text a home + index it (S, high).** Extend the `assets` Json shape (no migration) to `{kind,url,label,extractedText?,extractStatus?:'pending'|'done'|'failed'}`. Extend `indexDocument` to also chunk/embed each asset's text into the same `workspace-documents` corpus under a **new** `doc/<id>/asset/<n>/<chunk>` namespace, distinct from body chunks at `doc/<id>/<chunk>`.
- **Fix the own-doc RAG filter (S, high) — the one line that decides whether it works.** `docs.ts:71` filters out any hit starting `doc/<thisDocId>/` (to stop grounding on prior draft). Once the asset namespace exists, that filter would silently drop the very source-PDF chunks J-Doc1 needs. Change it to exclude only body-level `doc/<id>/` while keeping `doc/<id>/asset/`. Ship with an explicit test.
- **Inline full source text instead of top-k (M, high).** For assets **directly attached to the doc being generated**, skip semantic retrieval entirely and inline the full extracted text of every parsed asset as an "Attached source material" block (generous ~40k cap + visible truncation warning). k=4/2500-char similarity silently drops most rubric criteria; source grounding needs completeness, not similarity ranking. (Grounding on *other* workspace docs stays top-k.)
- **Async parse-status UI (S, medium).** Reuse the existing export-polling `useEffect` in `[docId]/page.tsx:48-50` to show a per-asset spinner chip → check / retry on `extractStatus`. A multi-second container parse with no feedback reads as broken on a phone, and scanned/corrupt PDFs need a visible retry path.

#### Document structure / templates

- **Add a `kind` + template registry (M, high).** `Document` has no `kind` field; `document-create` takes only a title. Add `kind String @default("blank")` (+ index), a `server/documents/templates.ts` registry (mirroring `server/scaffold/templates.ts`) with a `technical-design` entry seeding an H2 skeleton (Overview / Requirements / Architecture / System Decisions / Wireframes / Open Questions), extend `document-create` to accept `kind` and seed `content`, add a kind `Dropdown` on the create bar, and make `MODE_TASK.generate` preserve/fill the template headings when a kind is set.
- **Outline-then-sections generation (M, high).** `runDocumentAi` calls `runAiCompletion('document-generate', …)` exactly once asking for "the COMPLETE new markdown document" — no outline pass, no per-section expansion (no such pipeline exists anywhere in `server/`). For a genuinely detailed design doc this degrades to one shallow (or truncated) shot. Add a two-pass mode for `technical-design`: pass 1 → outline (H2 + one-line scope); pass 2 → one grounded completion per section, concatenated. Reuses the same call-site + RAG grounding per section; store the outline in `aiDraftLabel` for transparency.
- **Requirements-matrix scaffold (S, medium).** Tables are already solid end-to-end (`MarkdownView` renders them; `extractTables`/`xlsxFromMarkdown` turn each into its own named worksheet) — the only gap is that nothing scaffolds an `ID | Requirement | Priority | Source` starter. Fold a `Requirements` H2 + starter table into the template above and add one prompt line to keep/expand it rather than prose it away. No new engineering.

#### Wireframes / diagrams (highest-leverage single gap; L, high)

`MarkdownView.tsx` and `mdToHtmlBody` implement the identical narrow subset (headings/lists/quotes/tables/paragraphs) — no code fences, no images, no mermaid; `package.json` has no diagram dependency. AI-generated images only ever land in the asset side-strip, never inline. This blocks the named "wireframes" deliverable across author, phone-review, and export simultaneously. Proposal, in three parts:
1. Render ```mermaid``` fenced blocks in `MarkdownView` (client-side mermaid call — this app's own bundle needs its own render call; it isn't an Artifact page) so diagrams show in the editor preview and AI-draft panel.
2. Pre-render mermaid fences to inline SVG/PNG server-side before html/pdf/docx via a throwaway mermaid-cli container (mermaid bundled in-image since containers have `--network none`), reusing the existing `docker()`/`containerRender` pattern used for pandoc/chromium.
3. Instruct the generate-mode system prompt to emit mermaid fences for architecture/flow/wireframe diagrams.

#### Humanizer (S, low)

Confirmed solid: `document-generate` maps to the `documents` skill group, `skillPromptBlock` injects at the shared completion choke-point for every mode, and the builtin `humanizer` carries the ADR-0015 integrity boundary. The only gap is reachability — safe tone-polish is only available by choosing `rewrite` and typing an instruction (risking structural drift). Add a fixed `humanize` preset to `AI_MODES` that calls `rewrite` with a locked "polish tone only; preserve every fact, heading, and structure exactly" instruction. Client-only wrapper, no server change.

#### Export fidelity

- **Embed images/diagrams in exports (M, high).** Let `content` reference assets as standard `![alt](/media/name)`; add an image branch to `mdToHtmlBody` that inlines the local file as a base64 data URI (reuse the proven `brandLogoDataUri` pattern), and extend `containerRender`'s `buildInput` to copy referenced media into the temp mount so pandoc's native docx image embedding resolves. Today the single most "premium" element of a design doc is guaranteed absent from all 5 formats.
- **Stop pdf/html dropping links/code/footnotes (S, high).** The homegrown `mdToHtmlBody` (used by both html and pdf) has no `[text](url)` or fenced-code branch, while docx (real pandoc) supports both — the same doc exports correctly to docx but garbles in the two formats most likely to be handed in, with no warning. Add a link regex to `inline()` and a fenced-code branch to `mdToHtmlBody` (mirror the existing table two-line-lookahead), and mirror both in `MarkdownView` so the preview stops lying.
- **PDF page numbers + TOC (S, medium).** Drop `--no-pdf-header-footer` to restore Chrome's native page-number footer, and generate a TOC at the top of `standaloneHtml` from the heading scan already performed inline in `mdToHtmlBody`. A multi-page submission PDF with neither reads as unfinished.
- **Brand the docx (S, medium).** `renderDocx` takes no logo/template param while pdf/html both inline `brandLogoDataUri`. Generate/cache a per-workspace `reference.docx` (heading colors from the active DesignArtifact theme, logo in header) and pass `--reference-doc` via the existing mount. docx is the format most likely opened in Word for a hand-in — and the only one with zero on-brand styling.
- **Citation/source model (M, medium).** Grounded context is folded into the prompt as prose with no citation instruction and no `sources` field on `Document`. Require inline footnote citations (`[^1]`) whenever grounded `otherDocs`/`productDoc` is used and auto-append a generated "Sources" section. Pandoc parses footnotes natively (rides on the link/code fix); `mdToHtmlBody` needs a matching footnote branch for html/pdf parity.

#### Authoring / phone loop

- **Diff the AI draft (M, high) — top phone-review fix.** The draft panel renders `doc.aiDraft` via bare `MarkdownView` in a `max-h-72` box with no comparison. For a long rewrite/extend, the reviewer must re-read the whole doc and diff by memory — unworkable on a phone and a quiet violation of B-23 (approving a change you can't see). Reuse the existing `DiffView` component + `DiffLine` type from the MR-review flow with a small section-level (H2-block) or line-based differ over `(doc.content, doc.aiDraft)`; keep rendered-preview as a fallback toggle. (`server/mr/diff.ts` is git-unified-diff-specific — reuse its `DiffLine` shape, not its parser.)
- **Make revision history usable (M, high).** `DocumentRevision` is written on every edit/apply and pruned past 20, but grep shows **zero** reads anywhere — no list, no restore, no UI. Add `document-revisions-list` + `document-revision-restore` to the `DOCUMENT_OPS` whitelist and a conductor case that snapshots current content then restores the chosen revision (mirroring the apply-draft snapshot pattern), surfaced as a History slide-over with per-row `DiffView` + consent-gated Restore. Without this, a bad AI apply from a phone has no undo but retyping.
- **Wire up archive/restore (S, medium).** `Document.archived` exists and is indexed but is never set or read; the only removal is hard delete. Mirror the working `content-archive`/`content-unarchive` conductor pattern (a sibling module already has the full soft-undo) plus an archived-filter toggle and per-row action.
- **Search/filter + ⌘K (S, medium).** `documents/page.tsx` is a flat unfiltered list, and ⌘K's "docs" section indexes InfoSource context-docs (`InfoDoc`), not the Documents module (`DocumentEntry`) — a Document is unreachable from ⌘K by any path. Add a client-side title/content filter input (data's already loaded) and a `documents` section to `SearchPalette` navigating to `documents/${id}`.

#### Couplings

- **Add ticket + decision RAG corpora (M, high).** `RESERVED_CORPUS_COMMITS` enumerates every corpus that exists — there is no `workspace-tickets` or `workspace-decisions`, so tickets and ADRs are never embedded at all. This supersedes the prior scan's "excluded from the call" framing: the source data doesn't exist as a retrievable corpus. Add two `indexDocument`-shaped indexers (or reuse `institutional-memory` under a `decision/<id>` prefix for the cheap path) and extend `runDocumentAi`'s grounding to retrieve them for `technical-design` docs, so the "System Decisions" section grounds on real board + ADR content instead of inventing it.
- **Document↔Ticket link (M, medium).** No `documentId`/`ticketId` cross-reference exists on either model. Add optional `Document.ticketId` (indexed), a "Linked ticket" chip in the editor + a "Docs" list on ticket detail, and extend `runDocumentAi` to pull the linked ticket's title/description/acceptance-criteria into context. Removes the manual copy-paste of context on every run.
- **Reuse existing assets before regenerating (M, low).** `generateDocumentImage` unconditionally calls `runMediaGeneration` — no lookup against `StudioArtifact`/`DesignArtifact`/`ContentAsset`, burning budget and producing a fresh unapproved image even when a human-approved mockup already exists. Add an asset-picker modal (reuse `menuHandler.open` + the existing asset-grid) to pick-and-attach, keeping generate as the fallback.

### Suggested build order for the Document tool

1. **Unblock upload** (two-map pdf/docx edit) — cheapest possible, and nothing downstream is reachable without it.
2. **Text extraction + storage + asset-namespace indexing + the own-doc-filter fix** — the four moves that turn an inert PDF into retrievable, generation-visible source text (ship together; the filter one-liner is the make-or-break).
3. **Full-source inlining for attached assets** — so the generated doc reflects the *whole* rubric, not a top-k gist.
4. **`kind` + technical-design template (incl. requirements table) + outline-then-sections generation** — gives J-Doc1's "detailed" bar a real structure to fill.
5. **Mermaid diagram rendering (editor + all exports)** — the highest-leverage quality gap; makes output look like a real design doc.
6. **Export fidelity pass** — inline images, links/code/footnotes in pdf/html, page numbers + TOC, docx branding, citations (mostly S-effort, high perceived polish).
7. **Phone-review loop** — AI-draft diff, then revision history list/restore.
8. **Housekeeping + couplings** — archive/restore, list search + ⌘K, ticket/decision RAG corpora, Document↔Ticket link, asset reuse.

Steps 1–3 make J-Doc1 *possible*; 4–5 make it *good*; 6–7 make J-Doc2 *submission-grade*; 8 is durability at scale.

## Shared building blocks

Infra both tools need — build once, both journeys benefit. Where the second tool's use is inferred rather than a named gap, it's flagged.

1. **A throwaway-container parse/render harness (+ a real PDF/docx text parser on top).** Both tools already lean on the same `docker run --rm --network none` pattern — Design's `captureUrlScreenshot` (chromium) and the Document exporter's pandoc/chromium containers. The missing PDF/docx text extractor (Document's J-Doc1 spine — *zero* extractor exists in the repo), the mermaid pre-renderer below, and any future parse step all ride that one harness. Harden the invocation helper once (poppler for PDF; the already-pulled `PANDOC_IMAGE` in reverse for docx), and both tools inherit new parse/render capabilities. *(Parsing is a named Document gap; the harness itself is already shared.)*

2. **A mermaid/diagram renderer usable in docs AND design wireframes.** The Document tool needs it concretely and in every surface at once (editor preview, AI-draft panel, all 5 exports — none render diagrams today) — the single highest-leverage Document quality gap. The Design tool's J-D1 gap is precisely the absence of any "page / layout / information-architecture" surface, and a wireframe/diagram renderer is the natural home for that output. One client-side `MarkdownView` mermaid branch + one server-side mermaid-cli pre-render container serves both. *(Document use is a confirmed named gap; the Design-wireframe use is the natural second consumer, not yet an explicit Designer ask — confirm before scoping the Design side.)*

3. **A cross-module asset-reuse index + picker.** Document's `generateDocumentImage` always regenerates — it never checks `StudioArtifact` / `DesignArtifact` / `ContentAsset` for an already-approved image (a named Document gap). Design's design-memory gap is the mirror: saved `DesignArtifact`s are never indexed for reuse in new generations. Both want one index over the approved-asset tables + a shared picker modal (reuse `menuHandler.open` + the existing asset grid) so human-approved work gets reused instead of re-burned.

4. **The reserved RAG side-corpus pattern, extended.** `referenceLibrary.ts` already ships the exact `embed → RagEntry under a reserved commit → retrieve()` shape, and `RESERVED_CORPUS_COMMITS` already reserves an unwritten "inspiration library" slot. Document needs new `workspace-tickets` / `workspace-decisions` corpora (+ asset-text chunks); Design needs a `design-library` corpus. Same copy-paste-ready module, three new corpora — build the indexer shape once, reuse for all.

5. **Background-job + progress + push for long generations.** `server/content/queuedMediaJob.ts` (`runQueuedMediaAsset`: queued row → progress broadcast → finalize → `PushNotification`) already exists and is used elsewhere. Design's ~3-min inspiration capture blocks the browser tab today; Document's multi-second container parse/export needs the same treatment. Adopt the one pattern across both tools so long AI/media calls survive backgrounding + a flaky phone connection and notify on completion.

6. **A phone-first "review-before-approve" viewer.** B-23 (approve = consent) requires the reviewer to actually *see* the change on a phone. Two ready primitives already exist — `DiffView` / `DiffLine` (from MR-review) and Design's `LookPreview` (live theme/style render). Document's top phone fix is diffing the AI draft; Design's is a rendered before/after. Standardize one consent-time viewer (text-diff for docs, look-diff for design) so both journeys are genuinely approvable from a phone.

7. **The humanizer / skill-injection choke-point (already shared — extend reachability).** `skillPromptBlock` (`server/ai/registry.ts`) already injects the humanizer/tone/brand-voice skills into every Document AI mode through one shared choke-point, and it's the same registry both tools' AI calls route through — so any generative copy (including Studio landing/component text) can ride the same humanizer. The gap is reachability, not plumbing: expose a fixed `humanize` preset and point both tools' generative-copy paths at the existing choke-point.

## Appendix — per-journey scanner assessments (raw)

### design-from-zero

J-D1 ("build a UI from 0") has NO working end-to-end home anywhere in the codebase, confirmed at the file level, not just at the module-boundary level the prior scan described. Three distinct near-misses exist, none of which close the gap: (1) the Designer generates only token blobs (theme/style/animation) via a working, solid AI loop (generateTheme.ts/generateAsset.ts) but has zero mechanism to compose those tokens into a page/layout -- premades preview on fixed canned demo surfaces, never the user's app, and the Components section is explicitly a read-only library reference, not an authoring surface. (2) Studio's `landing`/`component` generators (server/studio/generate.ts) are the only place in the whole product that turns a text brief into actual UI markup -- but the output is hard-constrained to a single self-contained HTML blob (inline CSS only, no JS, no multi-page), stored as an opaque `{html}` Json blob on a `StudioArtifact` row and rendered only in a Studio iframe; there is no write-path from this artifact into a project's real repo/routes. (3) Greenfield project creation (`project-from-template`, ADR 0046) -- the literal 'start with nothing' moment -- is 100% non-generative: `server/scaffold/templates.ts` ships 4 hardcoded stack templates whose seed files are static hand-written skeletons (react-vite's entire starter UI is one `<h1>Hello from Workspaces</h1>`), and the Create-Project form collects only a name + template key, with no brief/description field anywhere in the wire shape. So today, describing an app and getting a real starting UI is impossible through any single feature; the closest a user can get is manually filing individual coding tickets in the board for each page/feature one at a time (a generic ticket->refine->plan->impl pipeline that has no notion of 'page', 'layout', or 'information architecture' as a concept -- confirmed by reading GOLDEN_PLAN_STAGE.md, which describes a generic per-ticket plan stage, not a UI/page-set planner).

### design-decent-to-premium

For J-D2 ("existing UI decent to premium"), the ingestion half is real: a URL or uploaded screenshot goes through a throwaway chromium container (server/designer/inspiration.ts::captureUrlScreenshot) or direct upload, and a vision model (image-critique feature) either extracts a look or compares two screenshots — this part works end-to-end and lands as either a DesignArtifact proposal or a UiReviewRequest that flows into the existing review-inbox → ticket pipeline. But everything downstream of ingestion collapses toward color-only: the extraction prompt (EXTRACT_SYSTEM) and save path (saveThemeProposal) only ever produce/persist a theme (30 color tokens) — even though a full DesignStyle schema (radius, shadow, border, density, font pairing, weight, tracking, motion, blur) already exists and is AI-generatable from text via generateAsset.ts, it is never invoked from an image. The compare path (compareDesigns) produces only a markdown critique stored as prose in UiReviewRequest.notes — there is no before/after render anywhere (though Gallery.tsx's LookPreview is a ready-made live-preview primitive that could render one), no component-level (button-vs-button) comparison despite the prompt asking for it, and capture is hardcoded to a single desktop viewport (1440x2200) with no mobile pass. The handoff into the coding pipeline that must actually apply the elevation is the weakest link: ui-review-to-ticket (conductor.ts) builds the ticket description from raw problem tags + free-text notes + bare screenshot URLs — it never touches or creates a DesignArtifact, so even a perfect vision critique gets flattened to English prose the implementing agent must re-derive spacing/motion/hierarchy from, rather than reusing the structured named-look mechanism designSystemDoc.ts already has for exactly this purpose. Net: "decent to premium" today produces a plausible-sounding text critique and, if you also separately import a look, a recolor — but never a rendered before/after, never the full premium dimension-set (spacing/type/motion/detail), and never a structured object the pipeline can apply deterministically.

### design-apply-and-iterate

The apply-and-iterate loop has exactly one real bridge from Designer work to the running product: rebuildDesignSystemDoc (server/designer/designSystemDoc.ts) writes an InfoSource('design-system') that stageRunner.ts injects into every pipeline stage's CLAUDE.md, plus an optional per-ticket TicketArtifactLink (server/orchestrator/artifactContext.ts, schema.prisma:1092) that lets a specific design/Studio artifact ride along with one ticket (UI exists: src/workspaces/board/[ticketId]/page.tsx LinkedArtifactsCard, backed by src/workspaces/_sync/ticketArtifact_server_v1.ts). Both are real and wired. But tracing the loop end-to-end for J-D2 ('decent to premium, with before/after, then iterate') it breaks at almost every joint: (1) 'Use in project' only rebuilds a passive context-doc — nothing writes src/index.css directly, so applying a generated theme requires filing a full ticket that runs the ENTIRE general-purpose pipeline (stageId starts at 'unrefined', same as a brand-new feature) for what is a fully mechanical token substitution the Designer already computed exactly; the only faster path is a manual clipboard-paste (exportCss in Themes.tsx) that exits the AI loop, the consent trail, and phone-usability entirely. (2) When a ticket DOES carry a linked artifact, the fidelity is uneven and in one case actively broken: a linked theme/style artifact renders its real tokens via buildDesignSystemDoc, but a linked Studio landing/component/thumbnail artifact has its actual HTML explicitly discarded and replaced with a one-line placeholder ('HTML omitted here; match its structure + copy') — the one artifact type capable of showing the coding agent real premium spacing/typography/motion is thrown away. And a linked 'animation' DesignArtifact silently loses ALL of its data (duration/easing/fade/offsets) because artifactContext.ts's theme/style ternary misroutes any non-theme kind through the style renderer, which reads fields an AnimSpec doesn't have. (3) The redesign-ticket path from the compare flow (server/designer/inspiration.ts compareDesigns → conductor.ts 'ui-review-to-ticket') never creates a TicketArtifactLink at all — the ticket gets raw screenshot URLs + a prose critique in its description, disconnected from the separate theme-extraction flow, so no structured diff ever reaches the agent. (4) Nothing closes the loop with visual proof: captureUrlScreenshot is only ever called from the compare/inspire ops (src/workspaces/_api/designerInspiration_v1.ts); no after-shot is taken once the pipeline finishes, so a human approving the final stage has no rendered before/after, only the pipeline's own text summary. (5) There is no N-variant generation anywhere in the Designer (theme/style/animation generators each return exactly one proposal per call; the existing 'A/B compare' only compares two already-saved artifacts you generated serially). (6) Component-level work has no home on either side: Studio's 'component' kind (server/studio/generate.ts) generates a generic marketing-site component from a brief, not a redesign of any specific existing app component, and even if it did, point (2) means its HTML never reaches the agent anyway. Net effect: whole-theme application works only through a heavyweight, undifferentiated ticket pipeline or a manual copy-paste outside the product's governance; anything more granular (a component, an animation, a premium diff) degrades to prose or is silently dropped before the implementing agent ever sees it.

### design-inspiration-mobile

Verified against real code (server/designer/inspiration.ts, generateAsset.ts, generateTheme.ts, designSystemDoc.ts, library.ts; src/workspaces/_api/designerInspiration_v1.ts; src/workspaces/designer/page.tsx InspirationForm; prisma schema DesignArtifact/Environment; server/rag/index.ts + server/content/referenceLibrary.ts + server/content/queuedMediaJob.ts for comparison infra elsewhere in the repo). Inspiration import works end-to-end for ONE dimension only: URL-capture (throwaway chromium container, hardcoded --window-size=1440,2200, desktop only) or screenshot-upload feeds a vision model whose prompt (EXTRACT_SYSTEM in inspiration.ts) asks for ONLY the 30 theme color tokens; the result is saved as an inactive DesignArtifact(kind:'theme') proposal the user activates. The compare op sends two whole-page screenshots to a vision model and gets back a markdown critique stored as a UiReviewRequest -- there is no rendered after, no component-level comparison, and (confirmed by reading generateAsset.ts's buildStylePrompt/buildAnimPrompt, whose exact DesignStyle/AnimSpec JSON schema already models radius/shadow/border/density/font/motion) none of that schema is ever populated from a captured reference -- it's discarded even though the code to describe it already exists and is used elsewhere (the manual style/animation generators). ### doc-quality-export-humanizer

For J-Doc2 (submission-grade export), the text/tabular backbone is genuinely solid and the humanizer is real: `runDocumentAi` (server/documents/docs.ts) enforces single-H1 + heading structure, grounds on other workspace docs + product knowledge, and the `documents`-apply-point skills (humanizer/tone-of-voice/brand-voice, server/ai/skills.ts:84-129) inject into every AI mode via the shared `skillPromptBlock` choke-point (server/ai/registry.ts:82) — confirmed wired, not just declared, with the ADR-0015 integrity boundary embedded in the humanizer's own instruction text. But everything past "clean prose + tables" degrades: there are TWO independent, divergent markdown renderers — a hand-rolled `mdToHtmlBody` (used for both html AND pdf, verified: `renderPdf` feeds `standaloneHtml(...)` which calls `mdToHtmlBody`) that only understands headings/lists/quotes/tables/**bold**/`code`-span, versus real pandoc (docx) which natively supports links, fenced code, and footnotes. So the same document renders with different fidelity per format: a citation link or a ```code``` block survives in docx but silently vanishes in the two most commonly submitted formats (html/pdf). Images/diagrams are worse than "unsupported" — they're structurally disconnected from the document body entirely: `Document.assets` is a side-strip list never referenced from `content`, neither renderer has `![]()` handling, and the pandoc container runs with `--network none` and no local image files mounted, so even a manually-added image markdown tag would fail silently. PDF export explicitly disables Chrome's own page-number footer (`--no-pdf-header-footer`) and there is no generated TOC despite real heading structure existing to build one from. docx gets zero brand identity (no logo/template passed to pandoc) while html/pdf do get the brand logo inlined — an asymmetry in the opposite direction. There is no citation/source data model anywhere (no `sources`/`references` field, no footnote-aware prompt instruction) even independent of the already-known PDF-parsing blocker, so a document that grounds on other workspace docs never surfaces that grounding as traceable citations in the output.
